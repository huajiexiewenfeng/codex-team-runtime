# Structured submission and concise progress

Requires upgraded Runtime and discovered `team_context.submit`, `team_context.report_blocker`, and `team_context.progress_summary`. This document does not install or activate anything. Old submit/notice/CLI routes remain compatible when these tools are unavailable; do not invent an adapter or create replacement team state.

First follow [Manager inbox routing](manager-inbox.md) for the verified effective installed team mode. In queue_first, the original Worker makes its durable structured submit then posts the exact submission to the inbox; the fixed native flow below is not applicable. Post/tool/bridge failure retains the submit and error, never falls back to native send/E03 prepare. An unavailable mode read for a known queue_first team is not legacy. Only verified legacy/observe uses the flow below; this text does not enable or switch modes.

Worker submits taskId, summary, files, verification (command/outcome/evidenceRef), artifacts (path/sha256/verification/evidenceRef), and gaps. Use truthful declarations, including failed/not-run checks and empty artifact lists where applicable. Keep a stable submission_id and exact content for retries; changed content under the same ID conflicts. Field errors include field and example; correct the indicated field before resubmission. Artifacts/checks are Worker declarations, not independent Runtime verification.

For new submissions, begin summary with the actual commit/baseline or artifact version; if unavailable, say so without inventing one. Describe actual plan deviations in existing fields; if none, explicitly write “偏离：无” (summary is sufficient). Do not put a fabricated gap in gaps. Retries of old submissions under the same submission_id retain their original content, including historical receipts; do not rewrite them to meet this new convention. No new required field or approval step is added.

For verified legacy/observe only, use the trusted runtime's `docs/optimization/functions-exec-submit-template.js` in one `functions.exec` invocation after filling notificationMode from the current installed mode, verified identity, actual evidence, stable IDs, baseline and existing human host-send authorization. It embeds the flow, has no imports/file reads, and calls internal tools sequentially. The mode declaration is a caller preflight, not authentication or an automatic mode lookup. Submission is committed before notice preparation; subsequent errors retain submitted state. `sendNow` must be fresh and non-replayed. Native host API authorization still governs send; Runtime never sends. Unknown send/registration outcome means reconcile the same attempt without resend. Only explicit accepted native evidence permits await-review notification status; a successful result ledger write alone does not.

Target ≤2 model calls is a measurement target, not validated savings. A missing tool blocks the candidate path. Installing tools, sending a real notice and proving a real host connection require their own authorized work. This local candidate has no real delivery proof. No atomic network transaction, exactly-once, background outbox or idle Manager wakeup is claimed.

Worker uses `report_blocker` with operation_id, task_id, blocker={reason,who,needs,evidenceRef}. It records a Worker report, not Manager `block` or `observe`, and sends no ordinary progress dialogue. Report scopes expire at submit/unblock/rework/approve/cancellation checkpoints; latestBlockerReport remains historical evidence. Expiry does not assert that the external problem was solved. Manager alone manages task blocking/unblocking and independent review/approval.

Manager/Liaison first read concise progress for the exact task_id at an existing user/review checkpoint, following [Results-first supervision](#results-first-supervision). It includes state/enteredAt, recent ledger activity/source, latest submission/review, and blocking scope. `agentWork.status=unknown` means no real-time host telemetry. Missing facts remain null/unknown; recent writes are not Agent computation. Read-only summary and existing dashboard snapshot share the same projection; no new timer, polling or model round is added.

Summary keeps managerBlocker separately from Worker reports. Task reads require exact task_id; omit it only when the user explicitly requests a team overview. Locate pending work and recover coordination through supervision-plan.taskChecks and pendingSubmissions; recovery or multi-task coordination is not an exception for an unfiltered summary. This is a caller rule, not a change to the MCP interface or program defaults.
