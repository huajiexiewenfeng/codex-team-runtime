# 轻量角色召回 MCP（历史 v1 设计）

本页仅保留 locator 增量的原设计与历史接口；不要按本页登记真实成员。当前 MCP 已停止暴露早期的 `team_context.register`，legacy 仅保留只读。现行 API 和 v2 分阶段接入边界见 [Team Context](team-context.md)。

本模块为 `manager-session` 增加按任务身份查找原状态文件的入口。Python 确定性处理索引、匹配和角色投影；没有 LLM、AGC、向量库、hook、定时器或后台巡检。

现有 `state.json` 仍是角色、配对、退出和业务状态的权威。索引只保存 `hostId + threadId` 对应的状态位置与成员引用，不保存第二份可编辑角色或完整聊天记录。MCP 不会自动调用自己；本轮目标是支持并测试前景召回，不承诺压缩后必然调用或跨月角色行为零偏移。

## 初始化与启动

需要可信的本项目 checkout、Python 3.10+ 和官方 MCP Python SDK。现有团队 CLI 仍需要 Node.js 22+。Python 的文件读取/索引核心不调用模型；MCP SDK 负责标准 stdio 传输。

在用户选择的独立虚拟环境安装本 checkout，不修改全局 Python 或 Codex 配置：

```text
python -m venv <独立虚拟环境目录>
<该环境的-python> -m pip install -e <可信-checkout>
```

下文 `codex-team-context` 指该虚拟环境中的命令（Windows 为 `Scripts/codex-team-context.exe`）；未激活环境时使用它的完整路径，或用 `<该环境的-python> -m codex_team_context.server` 替代。测试额外依赖可用 `pip install -e "<可信-checkout>[test]"` 安装到同一隔离环境。

显式创建新的空索引，其父目录需要已存在：

```text
codex-team-context init --index <新索引绝对路径.json>
```

再次初始化同一个文件应失败，不能用它覆盖原索引。已登记环境的索引丢失/损坏应报告错误并核对原文件，不自动初始化为空。

启动 stdio 服务：

```text
codex-team-context serve --index <索引绝对路径.json> --state-root <允许的状态目录绝对路径>
```

`--state-root` 可重复，限定可登记/读取的状态文件范围。选择确实存放团队状态的目录，不使用磁盘根目录或整个用户目录。不要把索引本身当团队状态文件。服务只按显式配置访问，不遍历用户其他对话或私人日志。以实际 MCP 启动进程的文件权限为边界；工具参数不是额外的读盘授权。

以上是接入说明，不表示已经安装到当前 Codex。要加入宿主 MCP 配置须由用户另外授权；本功能不要求修改 AGENTS.md 或安装 hook。全局 MCP 配置可能使工具元数据出现在其他对话中，`null` 消除了角色内容，不代表工具目录开销为零。

## 两个工具

### `team_context.register`

将**已经建立**的绑定登记到索引，不创建 Manager、Liaison 或 Worker。

```json
{
  "host_id": "local",
  "thread_id": "<当前独立任务的精确 threadId>",
  "state_path": "<原权威 state.json 的绝对路径>",
  "member_id": "<原状态中的成员 ID>"
}
```

先由宿主上下文核对当前独立任务身份，再匹配状态中对应的 active/bound 成员。不能传入自由填写的角色；Liaison 还需要原运行层的双向配对已经确认。邀请过期只限制确认发生的时间，不会让已确认的长期角色按期失效。

重复登记相同定位允许幂等；冲突定位不得静默覆盖。已退出成员不能通过登记重新激活。登记成功后调用 read 核对角色、成员和状态位置。首次角色激活、Liaison 确认或 Worker 成员建立后，在其各自已验证的独立任务上下文中执行此步骤；不会因此创建新任务或发送消息。

登记使用短时排他锁与原子替换，避免多个成员同时写索引时丢记录。锁竞争只有限等待；崩溃遗留锁不会自动删除或猜测过期。遇到持续 `INDEX_BUSY` 先核对写入进程与索引，不重新初始化来绕过；只读查询不获取写锁。此版本也不自动迁移已登记的状态路径。

### `team_context.read`

```json
{
  "host_id": "local",
  "thread_id": "<当前独立任务的精确 threadId>"
}
```

读取不需要记住 state 路径。先精确匹配索引，再读取对应的当前角色记录，不能按标题、部分 ID、目录名或聊天自述推断。

| 结果 | 含义与后续动作 |
| --- | --- |
| `null` | 当前索引没有该身份。普通未登记工作照常；已有团队角色依据时核对原状态定位，不能把 null 当成角色退出或新建团队的许可。 |
| `status: active` | 返回当前角色、成员/团队 ID、来源版本、状态位置、策略版本及简短职责。完整进度、派发资格和验收证据仍读取原运行层。 |
| `status: inactive` | 原登记已退出或解绑，不从历史提示恢复该角色。 |
| 工具错误 | 身份不可确认、文件/索引损坏或丢失、配对异常等。不是 null，也不是恢复成功；暂停受影响的角色操作并说明原因。 |

Python 中未登记结果为 `None`；MCP 返回一个文本内容块，其文本精确为 `null`、`isError:false`，不携带任何角色指令。正常角色结果同样为文本中的 JSON 对象；核心错误为 `isError:true`，文本中含 `{code,message}`，不能把失败当空结果。读操作不登记、不修改源状态、不刷新任何业务状态或计时器。

Python 校验恢复角色直接依赖的身份、绑定、配对与来源结构，不复制全部业务任务状态机；有效角色结果不是整个项目状态健康或当前派发资格的证明，后续业务操作仍由 Node 运行层完整校验。

## 前景召回节点

- 已建立团队的任务续接、跨轮“继续”或上下文恢复后，重新确认角色和原编排所有者。
- 分发、返工、验收前，如果当前角色信息缺失或可能过时，先 read；业务资格仍用原运行层检查。
- 授权建立/修改角色绑定后，登记并读回；退出仍走现有 `exitMember`，随后读取应为 inactive。

不用每次文件读取、每条工具结果都额外调用，也不以“今天读过一次”跳过后续压缩恢复。没有 MCP 时，保留原 `resume <state> <caller>` 入口；没有可信原路径时不要猜测或重建状态。

身份键是 **hostId + threadId**，不是 MCP 连接 session ID，也不是 Codex 的 session-tree 根 ID。临时子 Agent 可能继承父任务环境变量，不能据此登记/领取父角色。这里的身份保障仍是 `caller-declared`：调用方必须另行核对宿主身份，MCP 不冒充认证系统，也不能拦截绕过它的 shell 或原生任务工具。

## 验证口径

分别记录：

1. 确定性测试：索引重启可读、精确匹配、null 无副作用、来源变更、退出、错误分支、路径限制和真实 MCP 协议往返。
2. 受控行为案例：Agent 是否找到入口、读回后是否遵循职责；明确测试是否提供了 Skill/工具路径，不能称为自然召回率。
3. 实际宿主试用：真正的新轮次、自动压缩、重启续接及话题切换；未执行时保持未验证。

实际结果和证据限制见 [本轮验证记录](team-context-validation.md)。旧 Skill 的路径丢失观察仅保留了父任务摘要，不计为可复现基线或长期召回率测量；不要据此宣称原 Skill 一定忽视职责。
