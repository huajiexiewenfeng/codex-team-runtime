# 宿主汇报接入契约

状态：2026-09-05 设计审查基线，现已实现本地操作账本及注入宿主适配器的单次操作执行器；可执行范围见 [汇报操作账本](reporting-usage.md)。受控前台创建/暂停已有实测，真实后台自动化投递、无人值守停止和最终总结去重仍未完成接入或验证。

当前 reporting.actual 固定 unknown，offlineReceipt 不能作为宿主回执。接入时保留一个明确的汇报所有者和一个已知 automationId，不另建独立调度服务。

## 最小顺序

1. 核对当前团队、角色、用户汇报偏好、开放轮次与授权；记录精确所有者、automationId、bindingEpoch 和 intentVersion。
2. 将拟执行操作登记为 PREPARED，调用前重新核对版本和绑定。过期操作不发出。
3. 每个 automationId 最多一项未决变更。登记 DISPATCHED 后只调用一次宿主操作，不跨网络调用持有业务状态锁。
4. 核对工具返回的精确目标和实际状态；超时或结果不明记 UNKNOWN。先只读核对已知自动化，不能立即重复创建或发送相反变更。
5. 重新读取最新意图，再决定是否需要恢复或暂停。每次 heartbeat 也重新读取状态，不能依据旧消息暂停新工作。

本地 operationId 仅用于关联记录，不意味着宿主 API 支持幂等键。真实接入必须使用当前宿主提供的自动化工具，不手写调度指令或绕到外部常驻服务。

## 必须诚实说明的边界

- 本地版本锁可以拦住尚未发出的旧暂停；不能撤回已发出、稍后才在宿主生效的暂停。新轮次可能暂时处于汇报同步中，不能承诺零间断。
- 用户 reports off 跨轮次保留。角色退出与用户偏好是不同状态；退出还需核对自有调度的停止，不能指望已经退出的角色继续清理。
- 最终总结使用团队、关闭轮次版本和目标组成稳定键；发送结果不确定时先核对，不盲目重发。没有宿主幂等发送或送达凭据时，只能尽力去重，不能保证严格恰好一次。
- 普通历史查询不启动监督或汇报；Worker 结束不是 Manager 验收，只有实际收口且没有其他开放工作才考虑停报。

## 现场验收门槛

验证旧暂停准备后新开轮、旧暂停发出后新开轮、用户 off 后新开轮、创建超时但实际成功、暂停超时、退出后旧回执、最终总结已送达但本地落账失败。保留真实工具结果与未确定状态，不能用 fixture 或离线回执代替。
