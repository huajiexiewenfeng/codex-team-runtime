# E01 复核：任务待审不等于 Worker 持续运行

## 当前规则与候选根因

当前 `completion-notification.md` 已明确：已送达或进入审查后不再次发送，也不要引入 polling；同时另段写着“Wait at required Manager approval gates”。后一句没有就地说明，这是业务推进限制，而非要求 Worker 持续运行等待工具。

因此 E01 应定位为**成功路径终点的语义澄清**，而非添加新的通知协议或取消审批。可能的原因是两种“等待”被混用、上下文未召回或历史规则版本不同；目前不能判定唯一根因。当前代码内容不证明历史 Agent 当时读到了相同规则。

只对某条派发文本进行关键词检查，不能证明整个有效上下文没有要求等待。完整历史授权/待办与精确 attempt 对应关系尚未全量复核；因此 B0 支持研究此问题，但不应伪造为所有适用条件已确认的阳性样本。

## 拟议唯一差异（未应用）

在 Worker 正式提交成功路径旁就地澄清：

> 正式提交与精确通知 attempt 的真实送达结果已记录，且本轮没有明确要求继续等待或尚待执行的工作时，以“已提交待审”结束当前轮次，不为等待验收反向轮询 Manager。结束本轮不释放任务占用、不改变提交状态、不代表验收通过，也不允许开始新的未授权工作。等待批准是业务状态约束，不要求持续占用一个 Agent 轮次。

其余通知内容、模型、Runtime 状态机、验收标准、权限及拒绝恢复边界保持不变。不同时开启 E02 的消息数量改动或 E03 的接口封装。

## 离线评估与反例

`src/task-eval-completion.mjs` 的 `evaluateCompletionExit(sample)` 是离线评估辅助函数，不接入正常完成流程，不新增必须调用的检查或审批。输入为人工复核断言，每项保留证据引用；函数不会读取/认证引用，因此输出始终标明 `analyst-reviewed-assertions`，不能用作宿主授权。

| 场景 | 评估结果 |
| --- | --- |
| 提交、送达、同一次 attempt 与写入回执有证据；明确无继续等待要求和剩余工作 | 可进入试用方案审查，不自动激活 |
| 通知被拒或失败、未提交、attempt 不匹配 | 不适用 |
| 通知未知、缺写入回执、历史上下文未知或断言缺证据 | 证据不足 |
| 明确要求继续等待，或存在未完成工作 | 不适用 |

12 个反例/边界用例通过，包括严格值校验、无证据断言、无执行授权、无释放 Worker 和无自验收。它们验证确定性分类与保留边界，**不是 LLM 行为遵循测试，也不是节省效果验证**。
