# Team Metrics：具体消耗原因与证据链

状态：实现、独立审查及受控验收已完成。父需求见 [Team Metrics 基础版](team-metrics.md)。完整目标是「达到可观测性，并能定位 Token 消耗的具体原因」，其中原因定位指有来源证据的消耗构成和操作线索，不把时间邻近提升为精确因果结论。

## 问题与验收

当前 v1 已能汇总用量与团队归属，但丢弃了工具活动和计数来源行，不能解释高消耗片段。续接必须回答：哪条计数、哪个角色/任务/回合、输入/缓存/输出构成、附近发生了什么可观察操作、证据在哪里、下一步应核查什么。

1. 从显式指定的同一个 Codex JSONL 取得计数与脱敏活动元数据，不扫描无关任务。
2. 高消耗记录可按输入、非缓存输入、输出与 net 排序，显示实际时间、原生 turn/model（缺失未知）、历史归属和来源行。计数事件绝不冒充请求、工具调用或审查次数。
3. 说明消耗构成，定位大体积工具结果、相同调用/相同可见结果再次出现、压缩附近活动等证据。日志侧字节不冒充模型输入 Token；时间邻近不冒充因果；缺少版本和重复理由时不判浪费。
4. 输出可操作证据卡：观测值、关联方式、支持证据、限制、核查建议；无证据不得编造固定数量的根因或节省率。
5. JSON 与离线 HTML 表达一致、可下钻、转义安全，保留共享/未知、不修改业务 state/Registry。用受控场景检验原因定位，而非只有格式测试。
6. 兼容已有 v1 账本与 report；新格式明示版本。重复导入不重复计数，格式升级不改变原 record ID，不覆盖输入。

## 技术路线

仍使用 Team 内部确定性 Node.js 模块；不接外部 Trace/Eval Runtime、不调用 LLM Judge、不新增 MCP/Hook/定时器，不修改模型、团队权限、派工或验收门禁。

用量账本 v2 在 v1 字段外新增 `observations`。每项对应一个真正保留的计数 recordId，存储该计数的 sourceRef/usageLine/firstLine 以及自上一保留计数后观察到的活动。v1 读取原样兼容；重新导入生成新 v2 文件，旧数据没有活动证据时明确未知。

活动仅保留 kind、时间、行号、原生 callId、合法工具名、参数摘要、结果摘要与日志侧 UTF-8 字节数；不得持久化参数、命令、Prompt、回答、思维内容、文件内容或工具结果原文。摘要仅用于相等比较，不是身份认证或理由证明。原生日志未提供的 requestId/turnId/model 不反推。

当前宿主的工具返回主要是 `input_text` / `input_image` 内容块数组，而非普通字符串。对已确认的 JSON 数组格式，只在内存中序列化以计算摘要和 UTF-8 体积；数组摘要加类型域前缀以区别于普通序列化文本。数组体积包含 JSON 结构及可能的图片/引用编码，不等于输入 Token。未知独立对象格式继续保持未知。证据卡分别保留原始计数行和活动窗口终点，并展示各调用工具名、各返回的字节和行号，不仅给窗口聚合数。

工具调用与结果按真实 callId 对应；不执行日志中的代码。`functions.exec` 之类封装是一个已观察的宿主调用，内部代码提到的工具不自动计为已执行子调用。无法可靠对应的结果保持未知。尾部活动没有后续计数时不分配 Token。

真实日志中的 Token 通知可能晚于对应模型响应及后续工具返回。若唯一未匹配的原生 `token_usage_record` 与当前线程、已知 turnId 和五项原始计数一致，则保留 `nativeResponse: {responseId, turnId, line, association:'counter-match'}`，并以该原生响应行作为活动窗口终点；其后的工具结果留给下一窗口。没有唯一匹配时为 null，使用时间邻近边界，不猜最近响应。原生累计计数不再相加；此关联不证明某项工具输出具体占用多少输入 Token。

实际当前任务的授权元数据检查发现日志约 160 MiB（最大单行约 6.23 MiB），因此长期任务导入改为逐行状态机与分块读取。固定打开时文件字节边界，后续追加不混入此次快照；64 MiB 限制改为单行保护，不再限制整个文件。原文不整体加载或落盘，超长行明确拒绝，未完成尾行明确诊断。v1 的总文件限制仍是历史版本行为，不作为本轮验收终点。

报告 v2 新增 explanation：保留完整逐计数证据表，提供不同指标的高消耗排序、输入/缓存/输出算术解释、日志侧大结果、重复候选和压缩附近活动。解释使用 observed / temporal / candidate 级别，建议仅为核查建议；不自动修改开发工作流。一个 Token 记录只计入一次团队总量，多个解释标签可重叠，禁止相加。

## 验证场景

- 缓存占主导的大输入与非缓存输入高的片段分开排名。
- 一个大工具结果关联下一计数的邻近窗口，只展示字节与定位，不宣称其等于计数输入。
- 相同 tool+arguments 摘要、结果摘要相同形成重复内容候选；结果变化不得称同一内容；原因未知不称无效。
- 缺失/复用 callId、未知事件、部分末行、无工具证据、无原生 turn/model、跨线程隔离与计数重复均有测试。
- 升级前后计数与 record ID 不变；v1 与混合历史可用；任意原文哨兵不得出现在账本/JSON/HTML。
- HTML 恶意嵌套输入在输出目录创建前拒绝；局部钻取与窄屏检查；导出仍 READY-last。
- 用户另行确认前只使用 fixture。真实受控采样用于验证宿主字段与原因证据可用性，不以 fixture 成功替代实际结论。

## 与审计建议的关系

参考用户提供的 Manager Token 审计计划的三个层次：计数事件、可观察操作、工作片段。保留其「先测量再优化」「重复需核对内容和理由」「最多有证据地建议优化」原则。本次实现观测与解释能力，不执行其历史窗口审计指令，不迁入其他团队，不实施 compact/换模或削减验收。

- 合成团队场景验证了任务 × 角色归因、不同消耗排名、跨窗口数组返回、相同/变化结果候选、压缩证据、幂等合并、正文脱敏和只读导出。
