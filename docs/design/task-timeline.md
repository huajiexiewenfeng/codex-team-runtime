# 任务时间线与单变量优化设计

日期：2026-09-19。状态：设计与首个本地基线已建立；M1 已支持只读外层事件、明确 cell ID 的脚本续接、工具返回中报告的耗时、业务状态阶段与 JSON/Markdown 导出。内部进程完整边界及工作台集成尚未实现。本设计不启用任何协作行为优化。

## 目标

针对编码、构建、测试、文档等所有任务，回答：用户何时提出请求，谁在何时做了哪一步，这一步观测到多久，哪里在等待，哪里尚不能解释，以及某一项优化是否真的改善了结果。

这是现有 Team Metrics 的时间维度，不新增业务控制面，不依赖外部 Trace/Eval Runtime、LLM Judge、Hook 或常驻 Agent。任务事实仍来自 state/Registry；时间线只读。实验安排见 [优化台账](../optimization/team-flow-experiments.md)。

## 用户视图

用户已确认整合现有团队工作台，不增加新的入口（2026-09-19）。

- **任务详情 → 时间线**：默认按业务里程碑展示，展开到 Manager/Worker/Liaison 各泳道的工具调用、消息及日志间隔。
- **指标统计 → 任务时间线**：与「Token 使用量」「MCP 调用情况」并列独立 Tab（2026-09-22 已实现）。任务卡入口直接选中对应任务；切换或重新读取不重置所选 Tab，日报未绑定或读取失败不阻塞时间线。只请求当前所需报告，不自动采集日志。
- **后续耗时分析**：按团队、日期、任务类型、实验版本筛选，对比任务明细、阶段分布、覆盖率；不将所有数据塞进一张表。
- 每行：开始、结束、角色/成员、步骤、耗时、计时口径、证据入口、所属提交/尝试、完整性。
- 工具调用与相邻步骤之间的空档独立展示；未知不显示为 0，也不标成“思考时间”。可展开失败、重试、压缩、等待，不默认折叠掉异常。
- 产物就绪、Worker 提交、宿主接受通知、Manager 看见通知、开始审查、通过、用户交付是不同里程碑。
- 历史不完整任务照样展示已有证据，并明确缺少哪一端，不能宣称完整覆盖。

## 三种时间，不能混用

| 字段/口径 | 含义 | 不能解释成 |
| --- | --- | --- |
| `declaredAt` | 业务事件或调用者填写的时刻 | 文件真正持久化、消息真正送达时刻 |
| `observedAt` | 原生日志记录、工具调用/返回边界的时刻 | Agent 在此之前一直计算 |
| `reportedDurationMs` | 原生工具或构建程序明确报告的执行历时 | 与外层 exec/wait 时长可相加的独立耗时 |

UTC 保存，默认 Asia/Shanghai 展示，毫秒保留在 JSON，表格显示秒。人工摘要的约值不能升格为精确观测值。业务事件毫秒精度不等于其语义真实到毫秒。

本次真实案例：state 的 `executing` 从 16:16 开始，但 Worker 的构建命令到 16:31 才调用；submit 事件时间比实际 apply 调用早约 55 秒。前者是占位业务状态，后者是声明时间；两者都不能直接当执行或持久化边界。

### 计算规则

1. 只有起止端均存在、含义相容且可比较时才计算该 span。缺端则 `durationMs=null`，显示进行中或缺失；不能以 0 填补。
2. 一次任务总历时用请求观测到用户交付观测；缺任一端不声称完整总历时。未结束任务只给截至 asOf 的已过时间。
3. 阶段相邻里程碑之差是 elapsed，不等于该阶段实际 CPU、模型或工具工作时间。
4. 工具跨度必须依据同来源、host/thread、callId 唯一配对。重复 ID、孤立返回、时钟倒退保留诊断，不猜最近配对。
5. exec 的 yielded 返回只标成“首次返回”，不能当内部任务完成。后续 wait 与内部会话需精确 ID 才连线；仅通过源码中的工具名字不能证明内部调用发生。
6. 工具宿主 `durationMs` 与外层日志 span 分列；嵌套、并行、Manager/Worker 泳道均不可简单求和作为端到端耗时。完整兼容区间才可求并集；有缺口时只显示已知观测覆盖。
7. 同一角色相邻**已观察事件**的差值标为“日志间隔，未归因”；跨团队/多任务复用会话时，间隔还可能含其他任务，不自动归入当前任务。
8. 压缩记录只有完成点时，只展示点事件和前后间隔，不凭空给出压缩耗时。模型/宿主排队/审批等待同理：有明确边界才分类。
9. 不用“总历时减构建时间”宣称精确协调浪费。该差值可能包含必要分析、审批、验证、暂停、未观察工作。
10. 日报的端到端分布按交付日聚合并注明完整样本数；运行中任务另列。跨日、并行 span 不重复累计为团队工时。版本和任务类型匹配后才做对比。

## 数据契约（计划）

独立的只读 `task-timeline/v1` 报告，不改变业务 state schema。

```json
{
  "schemaVersion": 1,
  "teamId": "example-team",
  "task": {"roundId": "round-1", "taskId": "task-1", "kind": "build"},
  "timeZone": "Asia/Shanghai",
  "rulesVersion": "task-timeline-v1",
  "experimentId": null,
  "sources": [],
  "events": [],
  "spans": [],
  "coverage": {"status": "partial", "missing": []},
  "diagnostics": []
}
```

事件字段：稳定 eventId、sourceRef、来源 itemId/line、host/thread、member/role、turnId、task 关联证据、事件种类、declaredAt/observedAt、时间精度、call/attempt/submission ID（有才填）。只允许白名单字段。

span 字段：kind、起止 eventId、durationMs、timeBasis、parentSpanId、归属确定性、缺失原因。分类包括 dispatch/preflight/execution/verification/reporting/review/wait/recovery/unknown；工具名不够证明业务用途时保留 unknown。

任务关联优先级：明确 round/task/attempt/submission ID 与历史身份匹配 → 有证据的指定 turn/窗口 → unknown。手动圈定样本必须标 `analyst-scoped`，不冒充自动关联。Manager 同时协调多个任务，不能把整个轮次或所有空档自动归给单个任务。当前角色不能覆盖历史身份。

来源保存：显式授权的文件清单、读取字节边界/最后完整行、快照摘要、采集时刻、数据适配器版本。相同源事件再次导入幂等；相同 ID 冲突不覆盖。跨来源的相同消息仅凭相同摘要不能合并；需要真实关联 ID，否则显示可能重复。

## 采集与隐私

- 复用 `src/metrics-input.mjs` 的显式普通文件读取及大小边界模式、`src/metrics-observations.mjs` 的安全字段思想，不扫描全局 Codex 日志。
- 现有工具活动挂在 token_count 观察窗口内，尾部无用量计数时活动可能不进入结果。新时间线必须能独立于 Token 事件保留任务尾部，不直接把该集合称为完整活动日志。
- 白名单采集原生调用/返回元信息、state 事件及已有 MCP 观测。工具正文、源码、用户对话正文、隐藏推理不进入报告；不为分类而上传这些内容。
- 原生工具只提供总 duration 无开始时刻时，保留 duration 和 itemId，不用日志附近时刻拼造起止。
- 不通过要求 Agent 额外发消息、逐步骤填写日志或增加召回次数来获得观测。可在既有 Runtime 命令记录轻量时间，但采集失败不能阻塞交付或改变权限。
- 首个真实样本仅限用户指定的固件升级 Manager 与该打包 Worker、明确时间范围。扩大到其他任务需要现有授权清单覆盖，不默认采集其他团队。
- 本地真实样本存 `artifacts/`；公开设计文档只放通用契约。推送前另行检查真实身份、路径和业务信息，不随文档自动上传。

### M1 当前实现与验证

M1 当前实现边界：`task-timeline <manifest.json> <new-output-directory>` 只读取清单指定文件的固定字节边界，核对 session identity，按明确时间窗提取元数据。报告默认 `partial / analyst-scoped`。自 `task-timeline-v2` 起可用同来源/host/thread 下明确 cell ID 关联 exec/wait，重复或歧义 ID 不猜配；`asyncSpans` 的完成仅指脚本，不指内部进程或业务完成。`reportedDurations` 只接受结构化返回数据中的 chunk ID 与有限非负 wall time，独立保留，不拼造起止、不累加为构建总耗时。输入正文不保存，不执行、不分析脚本源码。仍不导入 MCP 服务端事件，不关联脚本源码里的进程轮询。日志间隔与调用区间可能重叠，不可相加。

v3 可选 `stateSource` 读取原始 state 快照，严格核对 team/round/task；`businessTimeline` 保留完整任务阶段及事件元数据，全部使用声明时间，不混入日志事件，不用业务状态推算原生执行边界。不会刷新 Registry 或修改 state。未指定来源的旧清单仍兼容。

2026-09-19 受控样本：固件升级打包端到端自动计算为 3,352,758ms，与人工基线一致；66 个外层调用、7 条脚本续接、29 条工具返回报告耗时。v3 加入 5 个状态阶段及 8 条业务事件，读取前后 state 摘要一致。声明 executing 1,501,979ms、submitted 731,811ms、reviewing 225,898ms，均不代表实际程序计算时间。构建约 8 分钟仍是人工基线中的独立原生证据，不能把脚本约 47 秒的生命周期误称为构建耗时。当前采集器尚未复现完整内部进程指标。未安装、未修改真实团队流程、未启用实验。

### M2：工作台集成（首个切片已实现，尚未完成）

新增可选 `processSpans` 与 `processRulesVersion: native-process-v1`，兼容旧报告。仅关联显式原生 `exec_command` 与 `write_stdin` 调用：要求同来源、host、thread、明确 session ID、唯一调用配对和退出码；重复 ID、缺端点、跨来源、倒序不能猜配。退出码非零表示进程结束但失败，不代表任务完成。观测历时包含宿主调用及轮询延迟，不是精确进程运行时间或 CPU 时间；不与外层调用相加。只保存 session ID、退出码和证据位置，不保存命令、标准输入或输出正文。Markdown 与工作台增加独立进程观测表。

## 验收底线

观察系统不能变成新的交付步骤。禁止为了统计增加 Agent 往返、定时器、业务审批或额外通知。无数据不是流程错误；统计展示错误不能停止真实工作。所有优化必须保留正式 Worker、忙碌保护、真实报告送达记录、独立验收及宿主权限边界。
