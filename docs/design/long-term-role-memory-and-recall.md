# 长期角色记忆与召回：用 MCP 恢复长对话中的团队身份

项目：codex-team-runtime / manager-session

日期：2026-09-10

性质：独立设计说明，基于当前本地实现；不是新增功能或已发布版本声明。

## 1. 我们要解决什么问题

一个开发团队可能运行数月，Manager、Liaison 和 Worker 的对话会经历多轮任务、上下文压缩、宿主重启和长期闲置。团队关系没有结束，但早期建立的角色约定可能已不在模型当前可见的上下文中。

由此产生的失败往往不是“不会写代码”，而是“忘了如何协作”：

- Manager 忘记自己负责协调与验收，重新变成直接实现所有工作的普通助手。
- Worker 完成开发后只在自己的窗口回答，不再向 Manager 回报。
- Liaison 忘记沟通边界，开始直接派工或将完成声明当作已验收。
- 成员记得自己是 Worker，却忘记属于哪个 team、leader 是谁、证据应交给哪个精确任务。
- 一轮开发已经完成，被误解为整个长期团队已经退出；下一轮又创建一套重复成员。

共同根因是：**将长期协作身份仅寄托在短期对话上下文里。** 对话摘要有容量和选择性，不能作为完整、可校验的团队登记表。这里不假设每次压缩都会遗忘，也不把所有协作失败都归因于压缩；消息未送达、角色未正式登记或旧版本连接也可能产生相似表现。

本设计的目标不是让模型永久保留全部历史，而是：

> 即使旧对话不可见，只要在关键节点调用召回入口，成员仍能从独立持久数据恢复“我是谁、属于谁、向谁负责、应遵守什么规则”，再依据业务状态继续工作。

## 2. 关键选择：把身份保存与身份使用分开

我们采用 **Skill + 确定性 Python MCP + Team Registry + 原业务状态** 的组合。

| 部分 | 责任 | 不能替代的能力 |
| --- | --- | --- |
| manager-session Skill | 规定何时召回、怎样核对结果、如何履行角色职责 | 不提供常驻存储或必定执行的触发器 |
| Team Context MCP | 接收精确身份查询，校验并返回角色上下文；提供受约束的管理操作 | 不主动调用自己、不调用 LLM、不自动发消息 |
| Team Registry | 持久保存当前团队、成员、leader、生命周期及入队确认 | 不保存全部聊天，也不代表原生任务正在运行 |
| Node 业务运行层与 state | 保存任务、轮次、队列、提交、验收与历史证据 | 不独立修改已链接团队的当前身份 |
| Agent 与 Codex 宿主 | Agent 判断下一步，宿主执行真实工具动作 | 读取身份不自动授予派工、部署或其他权限 |

长期记忆来自持久化文件与稳定协议，**不是 MCP 协议本身自带记忆**。MCP 是 Agent 访问这份记忆的标准工具入口；Python 代码承担确定性的读写和校验。

这也不是向量检索或“让另一个 LLM 总结历史”。已登记身份通过 `hostId + threadId` 精确匹配，不依赖语义相似度推断角色，因此不会因为标题相似、任务主题相同而认错团队。

## 3. 为什么不以 AGENTS.md、hook 或聊天摘要为主方案

### 3.1 不把每个团队的角色写进全局提示

全局 AGENTS.md 适合通用协作约定，不适合承载不断变化的团队名册、leader ID 和各个任务的职责。将这些内容全局注入，容易影响未参加该团队的普通对话，也会产生重复维护成本。

本设计不依赖修改全局 AGENTS.md，不把本团队身份默认赋给其他任务。

### 3.2 当前不引入 hook

hook 在宿主提供合适事件时可能提高触发确定性，但也增加安装、兼容、作用域过滤和生命周期维护成本。当前选择不依赖 hook；这是一项明确的轻量化取舍，而不是认定 hook 无价值。

相应代价是：**我们拥有可靠的召回入口，却没有“每次压缩后必定调用”的宿主级保证。**

### 3.3 不依赖 AGC 或完整历史回放

这是独立的团队角色记忆模块，不依赖 AGC。个人偏好、项目知识、完整需求与源码不进入角色 Registry。即便其他记忆系统不可用，团队身份仍可独立恢复。

历史对话可以辅助解释，但不覆盖当前登记。成员退出或规则更新后，旧摘要中的角色声明不能复活已经失效的身份。

## 4. 记忆保存什么，不保存什么

### 4.1 持久化正式团队集合

Registry 是 Manager 维护的正式集合，不是扫描最近活跃对话生成的临时名单。

它记录团队身份、正式成员及角色、精确宿主绑定、leader、成员生命周期、相关版本、入队确认和管理操作历史。职责由版本化策略代码生成并随召回返回，不把历史聊天自由文本直接当作新的行为规则。

成员增加、退出需要明确管理操作；闲置数月不自动删除，任务完成不自动退出。历史协作者也不会因曾经写过代码就自动加入。

### 4.2 紧凑的角色上下文

active 召回结果提供一个紧凑的角色上下文包（capsule），用于回答：

1. 我是哪个正式成员？当前角色是什么？
2. 我属于哪个团队？
3. leader 的精确 host/thread 是什么？
4. 当前共同规则与本角色职责是什么？规则版本是什么？
5. 我的入队确认及执行接入状态如何？
6. 对已链接团队，原业务状态和可信运行代码在哪里？

active Manager 额外获得正式名册，帮助恢复协调对象；普通 Worker 和 Liaison 不返回整份管理名册。

### 4.3 角色记忆不等于工作记忆

角色召回告诉 Worker “向哪个 Manager 交付”，不能单独回答“本次被授权修改哪些文件”。后者必须读取原任务 brief、业务台账和实际证据。

因此恢复分两步：**先恢复身份与责任，再恢复当前工作与授权。** 不把角色 capsule 膨胀成所有项目材料的副本，也不因拥有角色就继续旧的、已停止的任务。

## 5. 全员登记与首次确认

同一机制覆盖 Manager、Liaison 和 Worker，不只是给 Worker 补一条“完成后汇报”的提示。

正常流程如下：

```text
用户授权启用团队或加入成员
  → Manager 核对原生任务的精确身份
  → Manager 登记团队 / 成员
  → 每位成员在自己的任务加载共同 Skill/reference
  → 每位成员 read 自己的角色上下文
  → 成员返回 onboardingReceipt 和职责理解
  → Manager 核对真实回复来源并 confirm_ready
  → 重新读取，再进入独立的业务准入检查
```

只有 Manager 维护登记。Worker、Liaison 不自助注册、不自行选择 leader；Liaison 还需要其本人同意依据。Manager 自己也要完成 read 和确认。

回执绑定团队、成员、角色、绑定版本、leader 和规则版本。身份或规则不符时应对账，不能修改声明来强行通过。

这里必须区分：

- **registered**：已经记入正式成员集合。
- **ready**：当前版本的入队回执已核对。
- **可以执行工作**：还需满足授权、任务范围、占用、队列及真实投递等检查。

ready 不是未来永不遗忘的证明，也不意味着成员已经理解所有需求。Manager 读取一次更不等于所有 Worker 都已加载规则。

临时 Subagent 不因继承上下文而自动成为正式成员，不能使用父任务身份来召回并冒领父角色。

## 6. 压缩或长期续接后，如何召回

对已经登记的成员，恢复不需要重新创建团队或回放数月聊天：

```text
前台续接 / 已知上下文丢失 / 关键角色动作
  → 核对当前独立任务的 hostId + threadId
  → team_context.read
  → 判断 active / null / inactive / error
  → 恢复自己、team、leader 和版本化职责
  → 从原业务状态恢复工作与证据
  → 按角色与当前授权继续
```

查询形式为：

```json
{
  "host_id": "local",
  "thread_id": "<当前独立任务经核对的精确 threadId>"
}
```

这是示意参数，不可把标题、MCP 连接 ID、pending ID 或继承的父任务环境变量当成当前身份。也不能仅凭用户贴出的其他任务链接，就以该任务身份执行管理动作。

| 结果 | 正确处理 |
| --- | --- |
| active | 恢复角色，继续核对接入状态、工作与授权；不视为宿主在线证明 |
| null | 精确身份未登记；普通工作照常，已知团队工作先找回原定位，不自动注册 |
| inactive | 不恢复已退出角色，不从旧摘要重新启用 |
| 错误或不可用 | 暂停受影响的角色操作；不能伪装成 null、创建空表或绕回旧身份权威 |

read 无业务副作用：不登记、不更新访问时间、不刷新生命周期、不发消息。对未登记任务返回 null 能避免返回无关团队内容，但**全局注册的工具名称和描述仍可能进入其他对话的工具目录，不能声称 prompt 开销为零**。

## 7. 哪些节点需要召回

触发采用全员共同契约，并按工作节点控制频率。

| 节点 | 目的 |
| --- | --- |
| 首次入队 | 确认本人确实读到正确团队、leader 和职责 |
| 前台继续团队工作，或发现上下文丢失 | 避免凭不完整摘要恢复角色 |
| 身份、规则或负责人信息冲突 / 过时 | 以当前权威数据对账，而不是选择更熟悉的旧说法 |
| Worker 交付前 | 恢复自身归属、精确 Manager、提交和回报责任 |
| Manager 接收、审查、验收前 | 恢复独立验收责任，不把自报完成直接当作通过 |
| 其他角色相关协调且上下文已缺失或过时 | 恢复职责边界与当前所属关系 |

不在每次文件读取、每个工具调用前重复召回，不用定时器轮询记忆。上下文压缩本身并不是当前系统可保证捕获的事件；这里规定的是 Agent 在前台续接或识别缺失后的恢复动作。

新成员交接必须携带同一可信 Skill/reference 入口和经核对的本人 read 参数。关键业务路径再次要求召回，构成多处恢复机会，但这些机会仍依赖 Agent 使用规则。

## 8. 召回之后，如何恢复协作闭环

### Manager

恢复自己是团队负责人、正式成员对象及独立审查责任。随后读取原业务台账，区分排队、执行、已提交、审查中和已验收，再决定检查或返工。不因为原生任务 idle 或 Worker 最终回答就释放占用。

### Worker

恢复自己、团队和精确 leader；核对本次任务及证据后，先完成本人持久化 submit，再准备通知并通过获授权宿主工具向 Manager 发送。准备了通知不等于已发送，MCP read 本身也不会通知 Manager。

### Liaison

恢复沟通与进度解释职责，从可信状态回答用户，不直接派工或验收。相关工作关闭后停止普通进度汇报，但角色保留，用户仍可询问历史。

这使角色记忆服务于真实行为，而不是只在回复开头说一句“我是 Manager”。是否成功，应以随后的派工、回报、审查和授权边界是否正确来判断。

## 9. 确定性代码保证什么

Python 不让 LLM 决定查询属于哪个成员，也不让 LLM 自由改写 Registry。已编码的校验包括精确匹配、管理角色检查、结构和版本检查、回执核对、冲突拒绝、幂等请求及原子文件替换。

已链接团队采用明确的数据所有权：Registry 管当前身份，Node 管业务历史。Node 检查 Registry 投影，不能用旧 state 中的成员缓存覆盖当前名册；只读投影也不为了查询而改写原业务文件。

不过，“确定性”不是无限保证：

- actor 与 host/thread 是需外部核对的调用者声明，MCP 没有完成宿主级身份认证。
- 同等文件或工具权限的调用者仍可能绕开协议；真实访问边界来自宿主权限与文件权限。
- 回执证明声明匹配，不证明理解、未来调用或持续遵守。
- Registry 不检查 Manager 是否在线，也不保证原生消息送达或唤醒。

持久化代码与数据应分开。长期安装使用稳定版本的 Python 环境、Node companion 和 Skill；升级保留原 Registry/state，不为重启或连接异常创建第二个团队。安装文件成功不等于每个任务的 MCP 连接都已加载新版。

## 10. 最重要的边界：记忆可恢复，不等于自动想起

本方案将问题拆成两个不同层面：

1. **内容可恢复性**：正确角色不再只存在于旧对话，调用入口后能够从独立数据恢复。
2. **入口触发可靠性**：Agent 是否在需要时实际调用入口。

当前实现重点解决第一层，并通过共同 Skill、首次本人确认、交接提示和关键动作检查提高第二层的召回机会。它不能在没有 hook、强制注入或其他宿主触发的情况下，保证 Agent 即使连入口都忘了也会自动恢复。

因此我们的准确表述是：**降低长期角色漂移风险，提高跨压缩和长期续接时的恢复可靠性。** 不是“已经彻底解决 AI 遗忘”或“能够无人值守运行几个月”。

团队可以长期保留而不持续消耗模型计算。默认不启用定时器；若以后确有需要，必须由人确认最多24小时的固定窗口，续期再次确认。记忆模块不会用永久轮询来维持存在感。

## 11. 如何验证实际效果

协议测试、明示引导测试和自然召回测试必须分开记录。

| 层次 | 需要验证的事情 | 不能据此推出 |
| --- | --- | --- |
| 确定性协议 | 精确匹配、null/错误区分、版本/回执、只读无副作用、身份投影 | 模型一定记得调用工具 |
| 引导恢复 | 明确要求成员 read 后，能否恢复本人、team、leader 和职责 | 日常续接时会自然召回 |
| 自然长期协作 | 不提示工具名，在续接、压缩、重启、交付等场景观察实际行为 | 少量通过即可保证跨月不漂移 |

建议按 Manager、Liaison、Worker 分别记录：

- 自然召回率：需要召回的观察节点中，未经人工提醒主动 read 的比例。
- 身份恢复正确率：read 后是否正确识别本人、团队、leader 与当前规则。
- 职责执行正确率：是否遵守角色边界，Worker 是否回报、Manager 是否独立验收。
- 人工纠偏次数和恢复耗时。
- 每个恢复节点的额外工具调用与 Token 成本。
- 无关任务误触发、错误登记或角色冒领次数。

当前已有确定性协议测试和真实成员引导恢复证据，但尚不能宣称完成跨数月、多次自然压缩的长期效果验证。后续应优先用真实任务观察上述指标，再决定是否需要更强的宿主触发机制。

## 12. 总结

我们不是让模型“背住数月对话”，而是给长期团队建立一个独立、精确、可校验的身份恢复入口：

> Manager 维护正式团队集合；每个成员凭自己的精确任务身份召回；MCP 返回当前身份与版本化职责；Agent 再结合原业务状态恢复工作。

Skill 决定何时使用记忆，MCP 提供确定性访问，Registry 保留长期身份，业务运行层保留交付历史。四者协作，使对话压缩不再意味着只能凭摘要猜测角色，同时清楚保留“触发仍可能遗漏”的现实边界。
