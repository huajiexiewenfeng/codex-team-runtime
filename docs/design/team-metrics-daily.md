# 每日团队成本与长期角色召回观测

状态：需求已确认，分阶段实现；本文件不是功能全部完成的证明。

## 目标

用户可以按团队、角色、成员、日期查看实际已观测 Token，通过每次 MCP 调用的原因和证据判断角色记忆是否召回，并在相同口径下比较 Runtime 优化前后的成本与质量。统计独立于外部 Trace/Eval Runtime，不需要 Agent 定时器或 Hook。

## 四张表

1. 每日趋势：北京时间日期、团队、历史 Runtime 版本、统计规则版本、三类角色 Token、未知角色 Token、估算费用、验收数、召回覆盖率、角色违规数、数据覆盖情况。
2. 角色成本：选定日期下的 Manager/Liaison/每个 Worker、模型、输入、缓存输入、输出、总量、费用与缺失来源；可展开任务与团队公共开销。
3. MCP 调用：真实调用时间、精确成员身份、工具、触发原因、原因来源、关联事件、返回状态、证据位置和后续行为。
4. 召回有效性：可观察应召回节点、已召回、未召回、未决、身份命中、行为符合/违规/未知、分母覆盖范围。

所有表格中未知不是零。无日志不能判定无活动；没有观察后续行为不能判定遵守职责。没有完整观察窗口不能判定漏召回。

## 数据与时间契约

- 保留原始 UTC 时刻，默认 Asia/Shanghai 自然日，支持日期区间补算。单次范围上限 366 天。
- 已导入 ledger 为可重算的事实来源，每日输出是派生结果，不反向修改业务 state 或身份 Registry。
- 重复导入沿用稳定记录 ID 与现有冲突校验，不能把每次报告生成的累计值再相加。
- 单条用量按记录时刻归入日期，不声称能拆分一次跨午夜响应的精确分时消耗。
- 每日验收数量按 approve 事件时间计算；不能用当前任务状态回填所有历史日。
- 历史 Runtime 版本只能来自当时记录的版本证据。报告生成器版本、state.version、历史执行版本是不同概念。未记录的执行版本为 unknown。
- 缓存输入包含于输入，推理输出包含于输出。费用仅依据已配置且匹配模型/生效日期的价格版本估算，未配置或未知模型费用为 null；不将订阅消耗当账单。
- 团队公共开销保留在 Manager/Liaison 角色总量，不强行均摊给开发任务。
- 历史身份按已验证时间范围归属，不把当前成员名单倒投到几个月前。无法证明归属时进入 Unknown。

## MCP 原因与效果证据

候选原因枚举：onboarding、resume、post_compaction、before_dispatch、before_delivery、before_review、identity_conflict、manual、unknown。

原因来源必须分开：agent-declared（调用者声明）、event-supported（有独立事件支持）、temporal-candidate（仅时间邻近）、unknown。工具描述影响模型决策的心理因果无法由代码证明。

MCP 服务可记录“实际收到读取、返回命中/null/inactive/error”的事实，但不知道未发生的调用。召回覆盖率分母必须来自独立的压缩/交付/审查等可观察节点，不能用调用次数自身充当应召回次数。

三层效果分开：调用是否发生、身份是否命中、后续是否遵循角色。没有行为证据保持 unknown。压缩之后的调用与压缩相关不等于系统自动执行了调用。

现有日志采集只保留参数/结果哈希与体积，历史触发原因和结果正文不能从哈希还原。新入口可添加可选枚举理由及最小结构化观测，但不改变已有 read 的身份权限、返回值和 null 行为。不记录提示正文/工具正文，不为记录而扩大全局提示或破坏未登记调用无写入约定。具体采集开关及传输契约需实现前完成兼容性测试。

### 封装调用盲区

受控的既有脱敏用量样本中，工具观察只有 exec/wait 等外层名称，没有直接 Team Context MCP 名称。MCP 可在 exec 内执行，外层调用次数不是 MCP 次数，代码包含调用字符串也不能证明其真实执行。历史日报只能展示“可识别的直接调用”，不能把没有直接事件写成零触发。后续完整采集应采用显式启用的 MCP 端最小事件记录，补充准确的收到调用/结果事实；与原生日志关联时需要精确标识和去重，不能以相邻时间合并。未登记线程仍不得因全局注册而自动建立观测档案。

## 实施与验收顺序

1. 每日聚合纯函数及边界测试：复用现有归因，不更改旧 schema。
2. 日报 JSON/HTML 入口：日期筛选、逐日展开、角色/成员/模型表，空白日显示未采集；将已有 observation 的 MCP 调用与未知原因如实展示。
3. MCP 最小结构化原因与结果采集、应召回事件及行为证据：分别验证缺失、错配、完整窗口和重复事件，才启用有效性比率。
4. 只读工作台接入、授权成员日志清单、历史补算与版本对比；最后以真实团队完整链路验收。

不默认扫描全局会话，不自动采集其他业务团队。真实日志扩展授权与代码/合成测试开发解耦。展示需要同时明确数据来源、更新时间和覆盖缺口。

## 非目标

不接外部 Trace/Eval，不做 LLM Judge，不强制压缩后调用 MCP，不启用常驻 Agent、定时器或 Hook，不宣称精确的每工具 Token 因果或确定节省比例。

## 服务端采集与日报接入（已实现，效果评估待完成）

最小服务端采集已实现并通过单元与真实stdio验证，详见 [MCP观测配置与边界](../mcp-observations.md)。默认关闭，不会自行修改已安装服务配置。日报现可通过 options.json 的 mcpObservations 显式导入事件文件，按 registryId + teamId 隔离、按 eventId 去重、按北京时间完成日期汇总，在 MCP Tab 与原生日志分开展示。完整原生日志/服务端来源关联、应召回节点分母与后续行为评估仍未完成。无事件不证明无调用，matched 不证明遵守职责。

MCP 端观测应显式为指定团队启用，不因全局工具注册就记录其他会话。读取接口继续允许旧参数，只增加可选、枚举化的触发理由；未填理由为 unknown，不要求 Agent 另写一段说明。每条事件至少包含独立 eventId、UTC 时间、精确 host/thread、当时可验证的 team/member/role、工具名、声明理由及来源、返回分类、执行版本和策略版本。事件不包含 capsule 正文、用户提示、参数全文或异常堆栈正文。

未登记返回 null 的路径保持原有无写入约定；未登记调用只能在用户另行授权的原生日志样本中观察。观测存储必须与权威身份/业务 state 分离，日志不可用不能伪装成身份查询失败或身份丢失。记录失败需要暴露采集健康缺口，但不改变业务操作结果。重试、结果未知、外层exec封装和重复导入必须有分别的去重规则；不能把eventId不同的真实重复调用合并，也不能把一次调用在两个来源中的记录重复计费。

收益评估采用并列指标，不做单一“越来越好”分数：同类任务成本、Manager公共开销、可观察召回覆盖、明确角色违规、返工和验收结果。跨日任务成本以任务生命周期汇总另表显示，不使用当天Token除以当天验收数作为效率结论。统计规则变化时保留版本，比较页明确口径是否可比。
