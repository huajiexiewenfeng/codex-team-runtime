# 独立新任务安全入队：方案与暂不实施决定

日期：2026-11-11  
状态：已讨论并决定暂不实施；仅设计归档，不代表代码、Skill、安装或默认行为发生变化。  
源码核对基线：8a5eca8。受控宿主验证：Windows Desktop，codex-cli 0.167.0-alpha.3.2。

## 1. 问题与目标

现有未加载 Worker 就绪流程会导航打开聊天，导致用户从 Manager 页面切到 Worker。希望后台派发，不增加 Worker 启动/恢复轮次或 MCP 调用，也不让独立新任务进入正在执行的任务。

调查进一步发现后台发送与安全排队语义不同。曾提出为独立新任务接入原生队列；评审后认为它没有解决原始切页问题，并可能增加协商与维护成本，因此本次不实施。

## 2. 已验证的能力及边界

| 能力 | 受控结果 | 不能据此承诺的事 |
| --- | --- | --- |
| codex queue，已加载且空闲 | 自动启动轮次并回复 | 所有版本、宿主、权限场景均可用 |
| codex queue，执行中 | 原轮次正常结束后才处理下一条 | 断线、多发送者、用户并发下恰好一次 |
| 两次相同正文入队 | 产生两条消息并分别执行 | 宿主按正文自动去重；也未测同一原生ID重试 |
| notLoaded 时入队 | 入队成功，超过30秒未自动加载；打开后消费 | 入队成功等于已经执行 |
| 后台 send_message_to_thread | 自然notLoaded聊天加载并回复；前后UI仍是原页面 | 它是纯加载操作；全过程无瞬时页面变化 |
| 执行中后台发送 | 独立测试消息进入原轮次，最终一起回复 | 它是独立下一轮安全排队；本次未观察到原轮次取消 |
| 显示idle时后台发送 | 一次报 Cannot steer conversation ... without an active turn id | 已确定根因或所有idle发送都失败 |
| codex queue --resume | 入队后提示需要daemon或remote，退出码仍为0；仍notLoaded | 退出码0代表恢复成功 |
| thread/resume 协议 | 官方与本地类型支持加载，后续turn/start负责执行 | 当前Desktop已有外部可调用的同宿主后台加载入口 |

这些是少量隔离实验，不是生产收益评估。原始日志、会话ID、业务数据和本地运行台账不公开。实验未联系业务团队，未改宿主配置、启动daemon或启用定时器。

官方资料：[App Server](https://learn.chatgpt.com/docs/app-server)、[CLI reference](https://learn.chatgpt.com/docs/cli/reference)。当前公开Desktop工具未发现独立后台resume入口；read_thread不加载，open_in_codex面板排队不能当作会话加载。

## 3. 曾提出的最小候选（未实施）

### 3.1 范围

- 仅既有独立任务派发入口走queue，不通过分析消息文字猜类型。
- 当前任务澄清、回答和纠错保留原发送方式。
- 保留授权、归属、依赖、FIFO与在途约束；已有未收口任务不能因为原生可排队就提前塞下一任务。
- notLoaded沿用现有加载方式，所以候选本身不能消除该场景切页。

### 3.2 台账衔接

复用 operation_id、attempt_id、brief_ref、任务卡及派发证据目录。流程为既有准入检查 → prepare → 原生入队 → 保存queue ID和实际返回 → 在既有监督节点关联执行证据 → 原提交审查流程。

代码核查位置：
- [dispatch-runtime.mjs](../../src/dispatch-runtime.mjs)：prepare生成startTask并构造原send_message_to_thread请求。
- [dispatch-contract.mjs](../../src/dispatch-contract.mjs)：准入要求native idle，result当前有accepted/unknown/terminal-not-delivered/denied。
- [delivery-state.mjs](../../src/delivery-state.mjs)：投递恢复投影。
- [固定执行模板](../../scripts/manager-operations-functions-exec.js)：原发送与结果登记。

候选必须区分业务占位、传输接受和真实执行。prepare/startTask不能证明Worker已经开工；queue成功只能表示入队，不能直接套用现有结果语义。曾考虑增加传输记录（通道、queue ID、正文摘要值、时间、证据引用），但具体字段及旧状态兼容没有定稿。

### 3.3 去重与异常

- 同一操作和相同任务卡返回已有记录，不再次投递；同ID不同内容或目标报冲突。
- 已入队但登记失败，补登记而不重发；超时/断线的未知结果先核对。
- 只有明确未入队的证据才允许关联重试。
- 不以正文相同依赖宿主去重；不在失败后自动换普通发送。
- 本地持久化与CLI入队没有共同事务，崩溃窗口仍可能需要人工核对，不承诺恰好一次。

### 3.4 成本与验收约束

不增加Worker探测、接收确认、身份召回或进度汇报调用。程序记录投递事实；现有监督/提交证据确认执行，单纯active不能关联具体任务。

候选需验证：空闲投递、检查后并发变忙、重复调用、超时、结果登记失败、未加载、长文本/中文/特殊字符、旧记录兼容和回退。CLI须用参数数组，不能拼接shell或截断任务卡；Windows参数长度适配尚未验证。结果不明的尝试在回退后也不得换通道重发。

## 4. 评审：为什么暂不实施

| 判断维度 | 结论 |
| --- | --- |
| 原问题解决度 | 未解决notLoaded切页；已加载原本无须导航 |
| 安全收益 | 队列语义符合独立任务，但当前正常准入后发送竞争的生产频率尚无证据 |
| 协商成本 | 未证明减少；投递核对和恢复可能增加Manager调用与人工介入 |
| 系统复杂度 | 业务队列与宿主队列并存，新增映射、撤回、幂等、恢复和兼容问题 |
| 正常执行 | 未知结果不重发可能新增等待点；业务撤回后已入队消息的处理也必须解决 |

结论是“在当前证据和目标下存在负向优化风险”，不是已测得性能退化。不能把发现一个原生能力等同于必须接入它。

## 5. 已确认决定

1. 暂停此候选，不修改现有派发台账、状态机、Skill和Worker协议，不安装或切换默认通道。
2. 保留研究与实验结果。codex queue可以作为Watchdog提醒的候选通道，另行设计验证，不等同本次批准接入。
3. 切页问题继续限定为后台加载能力缺口，不用额外模型问候、第二套队列或切走再切回来掩盖。
4. 不擅自把notLoaded改成永久阻塞；现有行为本次不变。
5. 若有生产证据表明正确执行准入后仍因并发投递造成任务串扰，再评估有边界的改造，优先宿主原子能力。

## 6. 对后续Watchdog设计的启示

Watchdog的目标是发现遗漏和提供可处理提醒，不应改造成第二个派工系统。程序只记录可核对事实及矛盾；Manager判断任务是否完成及是否调整。提醒入队不等于收到、处理或问题解决。

后续讨论需明确：检查触发与成本、事实来源和新鲜度、异常去重、提醒待办如何复用、消息过期/撤回、Manager未加载时的降级，以及停止条件。不增加Worker启动与恢复负担。定时器仍默认关闭，既有最长一天和人工续期边界保留；本次文档不授权任何监控上线。
