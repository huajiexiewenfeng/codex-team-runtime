## 1. 目标与已确认决策

把用户指定的主任务设为长期 Manager，主要负责协调、持续审查、返工和技术验收。另设一个用户可见的独立沟通任务，负责需求讨论、问题解释、进度查询、周期汇报和传递用户已确认的决定。代码修改、构建、部署默认交给用户可见的独立执行任务。

两个窗口属于同一个 `manager-session` 功能的两种角色：沟通窗口称为 Liaison，监督窗口仍称为 Manager。新增 Liaison 不迁移或复制 Manager 身份，也不产生第二个调度负责人。

这不是一次性任务投递，也不只是汇总 Worker 的回答。Manager 在已确认范围内持续检查实际进展、向原 Worker 反馈发现、复验交付，直到本轮目标达成或遇到需要用户决定的真实边界。

已确认：

1. `manager-session` 是独立功能，可配合 PDC、任务调度及其他领域 Skill 使用。
2. Manager 与 Liaison 分别绑定各自的长期任务，可持续数月、协作处理多轮需求。
3. 只在用户显式退出时解除角色；一轮交付完成、会话闲置、应用重启或上下文压缩都不意味着退出。
4. 返工和阶段推进优先复用原 Worker，而不是每发现一个问题就新建任务。
5. 已确认范围内的审查、反馈、修正、复验不需要用户逐步回复“继续”。
6. Manager 可以读源码、查日志和做独立验收；业务实现与交付执行仍默认分发。
7. 不把技术验收通过等同于用户尚未执行的现场验收，也不把 Worker final 等同于目标完成。
8. 用户可长期在 Liaison 中讨论需求、询问进度与问题；Manager 保持对执行任务的监督。
9. 普通查询使用只读进度与证据，不逐次向 Manager 发消息；确认后的变更才交给 Manager 统一处理并回执。
10. Liaison 不只是播报员，也是需求与决策入口，但不能直接调度 Worker、批准技术验收或代替宿主权限审批。
11. 有开放工作轮次时需要周期汇报，并在发现重要事件后及时提示；本轮结束不解除长期角色。
12. Manager 确认全部工作完成后，Liaison 仅交付一次最终结论，自动停止周期进度与不再需要的汇报唤醒，不要求用户再手动关闭；保留问答能力。

当前 V1 默认在制工作上限 3 项，周期汇报和监督定时器均关闭。用户明确授权后才可配置节奏及固定期限，单次最多 24 小时，续期必须由人再次确认。15/5 分钟仅为可选节奏，不是默认运行或准点承诺。

### 需求背景

长期开发不止一次投递：同一个执行任务可能经历依赖澄清、阶段审查、具体返工与交付后的独立回归。用户需要保留这个监督闭环，同时有一个不承担执行调度的沟通入口。

本仓库只整理可复用的协作约束，不发布私人对话、任务标识、项目环境、凭据或部署授权，也不把历史任务自报的成功当作本项目的验收证据。

## 2. 方案选择

| 方案 | 收益 | 主要限制 | 结论 |
| --- | --- | --- | --- |
| 仅用一份角色提示词 | 最轻，容易试用 | 无法仅凭一次加载保证跨月、多轮和压缩后持续恢复 | 不作为完整交付 |
| 独立 Skill＋双角色绑定＋轻量状态与恢复＋原生定时跟进 | 沟通与监督独立，保留唯一调度者，可长期恢复 | 需要配对、进度同步和调度实测，增加少量上下文与同步开销 | 采用 |
| 将 Manager 全部并入 task-dispatch 或重做 PDC 调度 | 入口看似集中 | 改变既有生命周期，容易重复维护调度状态 | 不采用 |

新 Skill 不建设通用任务平台，不复制 PDC 的看板、Base Graph 或整个控制面。原生任务操作与定时运行仍通过宿主工具执行；本地支持程序只处理角色绑定、状态与指令记录、验证和恢复上下文。

沟通可选择逐次转问 Manager，或读取共享的进度投影。前者实现简单但仍可能中断 Manager 的等待；采用后者，只有已确认的控制请求才通知 Manager。双窗口减轻交互干扰，不自动增加 Manager 的深度审查能力。

## 3. 职责边界

| 参与者 | 拥有的职责 | 不应承担的职责 |
| --- | --- | --- |
| 用户 | 目标、范围与重大取舍；外部变更及宿主权限确认；指定的人工作业验收 | 在 Liaison、Manager 和 Worker 之间反复搬运消息 |
| Liaison | 需求澄清、问题解释、只读查询、周期汇报、记录和转交用户已确认的决定 | 直接调度 Worker、修改业务状态、宣布技术验收通过、代批权限或接管 Manager |
| Manager | 核对已确认范围、拆解、委派、依赖、持续审查、具体返工、独立核验、权威进度与技术结论 | 默认亲自实现业务代码；承担常规问答；替用户批准权限；无边界追加需求 |
| Worker | 在明确所有权内使用领域 Skill 实现、测试、构建或部署，并提供证据 | 自行扩大范围、替 Manager 最终批准、自动产生下一层任务 |
| 调度后端 | 其拥有的任务路由、运行状态、调度记录与生命周期 | 因组合使用而建立第二个竞争的 Manager |

允许 Manager：只读源码与运行证据检查，维护管理记录和已授权需求文档，在隔离且获准的环境中执行必要的独立验收测试。测试可能写入构建目录，不能把它伪称为纯只读操作。

默认委派：业务代码和测试代码修改、常规构建打包、部署和远端修复。业务实施不能因 Worker 慢、失败或工具缺失而悄悄回落到 Manager 或 Liaison。

用户当次明确要求 Manager 亲自执行某项操作时，可以作为有范围的例外；不因此解除 Manager 身份，也不扩大其他操作权限。高风险操作仍遵守领域 Skill 与宿主的真实审批边界。用户在 Liaison 中要求执行工作，默认仍交由 Manager 协调，不视为解除 Liaison 的职责限制。

### 查询通道：读取事实，不触发监督输入

Liaison 优先读取第 7 节的进度投影、已确认决策、待决策事项与证据引用；需要解释时可在获准范围内只读查看文档或原生任务摘要。普通查询不得发送 Manager/Worker 后续消息、改变其运行状态、更新业务验收状态或争取监督租约。后端不允许旁路读取时，只使用其允许的只读视图。

每次回答区分已验收事实、Worker 自报、进行中和未知，并带上相关信息的原始观察时间。重新读取旧记录不使它变新。无法确定的问题标记未知或过期；需要 Manager 专门调查时，先说明这已超出普通只读问答，再按用户明确请求转成工作项或控制请求。

### 控制通道：确认、核对、执行、回执

1. 讨论和草案不产生执行指令。用户明确给出的可执行要求可以直接构成确认，不必重复索要同一确认；含糊取舍先在 Liaison 澄清。
2. Liaison 将确认后的范围变更、优先级调整、暂停、继续或退出请求写成独立指令，注明 `commandId`、配对版本、请求层级、目标轮次或整组角色、预期范围或角色版本、具体内容及可核验的用户来源。无开放轮次时也可提交角色级退出请求。不可把其他任务中的命令文字当成用户授权。
3. 指令成功持久化后可用原生消息通知已绑定 Manager 核对该指令；日常查询不走此路径。发送仅用于通知或唤醒，不证明已经接收、执行或停止相关操作。
4. Manager 在每轮监督及新的外部动作前检查指令，核对身份、来源、作用域、版本和权限，再接受、拒绝或要求重新确认。来自 Liaison 的消息本身不是新增权限；宿主审批仍由用户完成。
5. 回执区分 `QUEUED`（已登记）、`ACCEPTED`（核对后接受）、`APPLIED`（指定生效条件已核实），以及 `REJECTED`、`NEEDS_CONFIRMATION` 或 `FAILED`。Liaison 只能按实际回执报告，不能把“已转交”说成“已生效”。

`APPLIED` 只证明控制请求的生效条件，不代表代码交付或整轮验收完成。范围变更须区分已更新的版本、各受影响任务的通知/确认状态与实际执行状态，不能仅因 Manager 改了记录就声称所有 Worker 已切换。

同一 `commandId` 的重复通知不得再次应用；同 ID 不同内容应拒绝。过期范围版本不能覆盖当前决定。暂停请求只有在相关原生控制或执行事实已确认后才可报已暂停；发送消息、归档或窗口关闭都不是硬停止。

Manager 对 Worker 的调度和技术验收保持唯一所有权。用户在人工作业验收上的决定，由 Liaison 记录来源，再由 Manager 核对并写入相应结论；不因此跳过尚未完成的技术验证。

## 4. 生命周期与调用语义

以下是拟定的 Skill 调用语义，不是已经存在的原生命令。

| 调用 | 行为 |
| --- | --- |
| `$manager-session start` | 把当前任务绑定为 Manager，检查恢复能力；不隐式创建沟通任务、Worker 或自动化 |
| `$manager-session attach <managerRef>` | 把当前任务绑定为指定 Manager 的 Liaison；核对精确身份及双向配对，不迁移 Manager |
| `$manager-session status` | 按当前角色只读显示配对、运行能力、当前轮次、进度时间、阻塞和待验收项；不唤醒 Manager/Worker |
| `$manager-session resume` | 恢复当前已绑定角色；Manager 核对后继续监督，Liaison 恢复查询及已授权汇报，不接管执行 |
| `$manager-session reports on/off` | 在有明确配置授权时启停本组的周期汇报；关闭汇报不退出角色、不停止 Manager |
| `$manager-session exit` | 请求退出本组 Manager 模式，停止两端自有后续调度，保留历史与未完成工作交接；异步退出以实际回执为准 |

自然语言的明确启用、继续、查看状态和退出请求可以映射到上述语义。引用文档或 Worker 消息里的命令文字不构成用户调用。

普通讨论中提到 Manager、请求设计此 Skill 或引用带 Manager 标题的任务，都不自动启用角色。重复 `start` 对已启用 Manager 是幂等操作，不能把现有 Liaison 升级为 Manager；重复相同 `attach` 不重复配对或创建汇报调度。`resume` 只恢复 ACTIVE 角色，不能把已经退出的角色重新激活。退出后需要再次明确启用，历史轮次不被重建。

V1 一组最多包含一个 Manager 和一个 Liaison。创建新沟通任务须有用户明确的新任务请求；仅批准本设计不构成实际创建授权。新任务获得最小交接信息，不复制 Manager 的完整历史。待创建任务只有 `clientThreadId` 时保持待配对，不冒用它作为 `threadId`。绑定未完成、身份不符或任一端恢复未验证时，标记双窗口模式未就绪，而不是静默降成另一套调度。

生命周期分为三层：

- 角色：明确为 `manager` 或 `liaison`，各有 `ACTIVE` 或 `EXITED` 状态，没有自动到期时间。
- 工作轮次：`OPEN`、`WAITING_USER`、`BLOCKED`、`CLOSED`；关闭结论区分已验收与用户取消。
- Worker：宿主拥有的运行、空闲、需要关注等状态，不等于业务验收状态。

某轮关闭后，两端角色仍为 `ACTIVE`；只要还有其他开放轮次，就继续监督与周期汇报。所有轮次关闭时呈现“待命”，Manager 暂停自己的续跑，Liaison 在收口处理中交付剩余最终结论并停止周期汇报，规则见第 5 节。新的已授权轮次可按已确认的持续配置恢复调度；新的独立需求建立新轮次，原需求的修正仍留在原轮次。数月后的普通查询不自动重开已验收轮次。

退出不是取消：先保存已有 Worker 绑定与已知状态，再解除本组角色。运行中的任务不会因退出而被宣称已经停止；如果用户还要求取消，使用实际支持的控制方式，能力不足就说明限制。两端自己拥有的后续自动调度必须关闭；其他独立所有者的调度不能擅自接管或停止。

在 Liaison 发起整组退出时，按已确认控制请求交给 Manager，实际生效前只报待处理。Manager 不可达时不得伪称整组已退出。用户只要求关闭沟通窗口、解绑 Liaison 或关闭汇报时，不影响 Manager；窗口不可见、关闭标签或短时离线本身都不解除任何角色。

若某端已完成角色退出但关闭自有自动化失败，该端仍记录 EXITED，恢复入口不得继续执行角色动作，并单独报告清理未完成；不能把部分退出写成整组退出成功，也不能把“已退出角色”写成“所有运行都已停止”。

## 5. 已授权范围内的监督闭环

每轮先明确目标、作用域、非目标、验收标准、领域 Skill、执行所有权和权限边界，再开始调度。

1. 恢复并核对：读取最小管理上下文、待处理控制请求及已有回执，核对真实 Worker、项目与工作区状态。
2. 定义工作：拆出可独立交付的工作项，注明依赖、证据要求和批准者。
3. 委派或继续：复用适合的原 Worker；新任务仅用于明确独立的结果或经确认的替换。
4. 观察：优先读取宿主的紧凑状态快照，保留游标；只有阶段变化、错误、关注或审查需要时深读。
5. 持续审查：执行中可以审查已产生的代码、计划与测试，发现问题及时反馈；并发读到的临时状态须在稳定交付时复核。
6. 返工：把发现发回原 Worker，包含证据、影响、最小修正和验证条件，不仅说“再检查一下”。
7. 独立复验：交付后检查实际产物、改动边界与验收证据；必要时亲自复跑或委派独立 Reviewer。
8. 收口：符合冻结的验收标准才批准，解锁依赖或关闭本轮；否则继续同一闭环。

每次重要状态或结论改变后更新进度投影；普通观察无变化时保留事实与变更时间，只更新真实的观察时间。新的调度、返工、验收动作前再次检查已确认控制请求，防止继续按旧范围执行。

原生受管工作项使用以下业务状态：

`READY → RUNNING → SUBMITTED → REVIEWING → APPROVED`

`REVIEWING → CHANGES_REQUESTED → RUNNING` 表示返工；无法推进时记录 `BLOCKED`。用户明确移除的工作项记录 `CANCELED`，不能假装已批准。

Worker final 最多表示 `SUBMITTED`。只有 Manager 或约定的批准者完成审查才能进入 `APPROVED`。PDC 工作项沿用 PDC 自己的状态定义，新 Skill 只引用，不另写同义副本。

### 多任务监控与审查负荷

监控使用紧凑状态，审查才按需深读。活动集合轮转收集，优先处理暂停等控制请求、权限与失败、阻塞和可解除依赖的交付；普通运行中的任务只更新状态，不反复阅读完整历史。不能长期只等待一个 Worker 而遗漏其他任务。

V1 默认在制工作上限为 3，覆盖执行中、已提交待审查、审查中和返工中的必要工作项。达到上限先审查和收口，再启动新项；阻塞项如需停放须明确记录，不能假装批准以释放依赖。用户可调整上限，任何并发仍须服从工作区与共享资源互斥。

当前宿主一次紧凑等待最多支持 8 个任务，这是接口的批量大小，不是 Manager 的质量保证或总体并发上限。超过一批时分组轮转并记录各任务最近观察时间，避免一批的长等待占满全部监督时间。

### 何时找用户

以下情况需要用户介入：新增业务范围、变更既有重大决策、跨越项目所有权、缺失必要输入、权限确认、外部不可逆操作或人工作业验收。Manager 将问题、依据、影响范围和待决定内容记录为待决策事项，由 Liaison 集中说明；宿主审批仍定位到原任务的真实审批入口，不代点。范围内的普通缺陷修正与复验由 Manager 自主推进。

目标已达成时主动收口。与目标无关的改进作为后续建议，不临时加进验收。连续得到同类失败且没有新证据时，先改变诊断方式、缩小验证或请求决策，不能无限发送同一句“继续修复”。

### 交互隔离与运行时间

用户在 Liaison 中聊天只影响 Liaison 自己的当前轮次，不应向 Manager 注入普通查询或向 Worker 传播暂停。Manager 持续做已授权范围内安全且必要的下一步，不因一次投递、一次 Worker final 或用户正在其他窗口讨论而提前结束监督。

独立任务各有上下文，可并行运行；官方也建议用旁路对话查询状态，避免打断主任务。这是双窗口设计的能力依据，不代表本规格中的角色配对、共享记录或自动汇报已经由宿主内置。[OpenAI 官方长期任务说明](https://learn.chatgpt.com/docs/long-running-work)

### 周期汇报、重要事件与监督续跑

用户最新确认：默认不启用定时器，优先使用 Worker 完成/阻塞通知和用户主动查询。V1 的定时跟进仅为可选能力，必须另行获得本次定时授权，确认固定起止时间且期限不超过 24 小时；续期需人再次确认，未完成工作或用户沉默不能自动续期。启用前须验证宿主能到期停止后续唤醒，无法验证则保持关闭，不以提示词自检或另建续期提醒替代。讨论规格、创建角色或开始新轮次均不授权定时运行。

| 机制 | 所在任务与默认策略 | 必须遵守的边界 |
| --- | --- | --- |
| 活跃监督 | Manager 使用有界等待与事件处理持续审查；每个等待不超过 60 秒 | 检查控制请求、覆盖活动集合、使用游标；不把无变化超时都发给用户 |
| 监督续跑 | 默认关闭；明确限时授权后可选原 Manager heartbeat，每 5 分钟检查 | 最多 24 小时，人工续期；不新建另一 Manager，不重复调度 |
| 周期汇报 | 默认关闭；明确限时授权后可选 Liaison heartbeat，每 15 分钟简报 | 最多 24 小时，人工续期；只读进度，不接管监督 |
| 重要事件 | Worker 向精确 Manager 提交完成/阻塞证据；Manager 按授权向 Liaison 转交重要结论 | 不依赖定时器；发送结果不明先核对，保留待处理，不默默追加轮询 |

每份进度至少说明：本轮目标、已验收项与总项数、正在执行、待审查或返工、阻塞与待决策、下一步，以及各相关事实最近观察时间。工作项分母和验收结论取自当前范围版本；不编造整体完成百分比或没有依据的预计完成时间。

仅在有效定时授权内、用户明确要求每期汇报时，即使没有新进展也输出简短状态，例如仍处于构建阶段、已持续时间及最近一次确认。默认不周期唤醒。`observedAt` 和 `changedAt` 分别表示观察与事实变化，不以生成简报或读文件的时间刷新它们。观察时间早于一个配置的汇报周期时标记过期；无论是否过期，未知运行状态都不得伪称正常。

已启用的定时器在固定期限到达、用户撤销或全部工作收口时停止；期限到达即使仍有未验收工作也不得自行续期。仅关闭部分轮次且授权尚有效时继续按授权跟进；尚未送达的最终结论保留待交付，不为此延长定时授权。到期不伪造验收，也不退出角色。

原生的同任务定时跟进支持分钟级周期；本地文件工作要求电脑与应用保持运行。上述 5/15 分钟是本设计可配置的目标节奏，不是严格实时承诺。[OpenAI 官方定时任务说明](https://learn.chatgpt.com/docs/automations?surface=app)

实际调用优先使用返回原任务的 heartbeat，保存调度 ID、目标任务、职责与配置来源；更新已有调度而非重复创建。不手写系统 cron、Windows 计划任务或常驻服务，也不把原任务 heartbeat 静默替换为每次新建任务的独立调度。后者只有在用户明确选择且与后端规则相容时另行设计。

周期报告行为与宿主通知设置分开保存和操作，不把“每期生成进展”误配成只通知失败；关闭周期汇报、静音通知、退出角色和取消执行是不同动作。PDC 已拥有监督运行时，不额外叠加原生监督 heartbeat，按第 6 节核对所有权。

### Manager 完成后的自动停止

1. 完成依据是 Manager 针对当前范围的业务验收结论，以及没有其他开放轮次；不是原生任务变成空闲、某轮回复结束、Worker final 或 Manager 暂时失联。仍有待审查、返工、阻塞或待用户验收时，不得伪称全部完成。用户明确取消的工作按取消结论收口，不写成验收成功。
2. Liaison 检出有效的全部完成结论后，立即停止普通周期进度，在收口处理中向用户给出一次最终总结，并暂停自己拥有的汇报 heartbeat、核对实际调度状态。已报告同一完成版本时不重复总结，不保留“每隔 15 分钟醒来再说已经完成”的循环。
3. 记录完成范围版本、最终报告的交付/待确认标记，以及逻辑状态 `STOPPED_FOR_COMPLETION`；原生调度是否成功暂停另行记录。暂停失败时如实提示一次清理异常，不宣称调度已停。已排队的旧周期触发先检查完成状态，停止普通汇报与重复通知；发送结果不明先核对，不盲目重发最终结论。
4. 停止前重读当前范围、配对及定时授权；旧完成事件不能关闭另有有效定时授权的新工作。新工作本身不延长期限，也不恢复已停止的调度；提前完成、撤销或到期后重新启用均须人明确确认新的定时授权。禁止滚动续期、换 ID 重建或预先串联多天。用户此前关闭汇报的选择须保留，历史查询不重启自动汇报。

这里停止的是本轮工作对应的自动进度及定时唤醒，不退出长期角色、不归档或关闭沟通任务。两端仍可响应用户的新消息。最终报告与暂停操作发生中断时分别保留真实状态，不把“已发总结”和“已停调度”当成同一件事。

### 运行条件与降级

长期身份不等于模型全天运行。自动化权限、目标任务绑定、同一任务忙碌时触发的合并或延迟、重入和通知送达，均须在本机受控实测后确认。不能仅凭 Skill、恢复 hook 或第二个窗口宣称持续在线和准点汇报。

应用关闭、设备休眠、权限或额度不足可能导致延迟；恢复后核对真实任务，合并漏掉的周期为一次当前报告，保留原始观察时间，不伪造过去的准点汇报。Manager 的进度过期时，Liaison 说明失联或待核对，不擅自接管；Liaison 不可用时，Manager 继续已授权监督，将未送达事项保存在记录中。

自动化未配置或实测失败时显示“角色已启用，自动跟进/汇报未就绪”，给出手动查询或恢复入口；这属于明确降级，不算周期汇报验收通过。不增加强制自动续跑的 Stop hook，也不绕过宿主权限或用无穷忙等代替调度。

## 6. 与现有 Skill 的组合

### 6.1 领域能力与执行位置分开

领域 Skill 决定“怎样做”，Manager 角色决定“由谁做、何时审查”。Liaison 可在其只读职责内组合查询类能力，接收开发请求不意味着在沟通窗口运行实施流程。Worker 的交接说明包含适用的 `project-develop`、`project-fix`、DevOps 等 Skill，以及自己的来源、范围和验收条件。

不假设 Skill 有函数调用栈：在沟通或管理任务加载开发 Skill，不代表它已在独立任务执行。真正的 Worker 需要原生任务创建或向已绑定任务发送消息。

### 6.2 原生受管适配器

在单项目或不使用 PDC 调度的场景，由 `manager-session` 内部的轻量适配规范调用宿主的项目列表、任务创建、等待、读取与发送消息能力。

Worker 是用户可见的独立任务，不用隐藏子代理或 fork 冒充。新建时使用清晰且与交接标题一致的名称，并返回宿主的已创建任务入口；除用户明确选择外不覆盖模型或推理设置，也不自动置顶、归档或重命名已有任务。

这不是把现有 `task-dispatch` 改成受管模式。可以沿用其“最小充分、可独立执行”的 handoff 结构，但受管任务有自己的反馈与验收契约，不能复制“永不回读结果”的终止条款。V1 不要求修改或安装 `task-dispatch` 才能运行。

### 6.3 task-dispatch

保留当前 `task-dispatch` 的投递即止语义。当用户明确要求“只发出去，不跟踪”时可选用它，该项记为未纳入本轮验收，而不是把投递成功记成工作完成。

如果某工作项是本轮目标的必要交付，就不能用投递即止代替受管执行。可以创建受管原生任务，或在用户明确授权后接管已有任务；角色启用本身不自动接管历史任务。

公共 handoff 协议的物理抽取不是 V1 的前置重构，避免为了复用一份提示词先修改多个独立 Skill。

### 6.4 PDC

PDC 项目知识、需求流程和领域 Skill 可由 Manager 与 Worker 分别在其职责内使用。只有符合 `project-task-dispatch` 路由条件的工作才使用它的跨 Project 调度。

接入一次 PDC Dispatch 时：

- 明确本轮逻辑 Manager 的唯一所有者，并遵守 PDC 的 placement、租约和前置门禁；不能因为存在角色标记就省略它们。
- 活动轮次可在合法 Manager 任务按 PDC 支持的入口协调；角色跨轮持续，不要求单次 PDC Dispatch 同样持续数月。
- PDC manifest 拥有其工作项、依赖、finding 与批准状态；`manager-session` 只保存 Dispatch 引用和本轮验收映射。
- 不再向同一 Worker 启动第二套调度循环，不重复发送返工，不另建第二份看板或镜像业务状态。
- 已有后台 Manager 或其他租约所有者时，不抢占；须完成明确的停止/交接，或保持只读观察。
- Liaison 只读取后端允许的进度、证据和待决策视图，不获取 Manager 租约、不执行会接管运行的入口，也不因周期汇报另起监督循环。进度投影须带 PDC 权威记录引用与版本，不能成为第二个可编辑的工作项状态表。
- 若 PDC 的 placement、后台模式与当前宿主规则不能兼容，标记该组合未就绪；不得伪造绑定或静默改选另一种授权。

V1 不改写 PDC 自己的实现。原生模式可独立使用；PDC 组合必须单独验证，通过前不得宣称无缝集成。

## 7. 持久状态与上下文预算

两种角色分别按精确的 `hostId + threadId` 绑定，不按标题、当前目录或“最近一个任务”推断。双方记录对应任务引用及相同配对版本；不匹配时停止控制投递而非猜测对象。新任务、fork 或 Worker 不自动继承任一角色。显式增加 Liaison 是配对，不是 Manager 身份迁移；自动跨任务迁移仍不在 V1 范围内。

运行目录为经用户配置和批准的 `<runtimeRoot>/<hostKey>/<threadId>/`，两端各有自己的角色目录；共享工作与控制记录以 Manager 目录为锚点。默认建议放在当前 Codex 用户数据目录下的 `manager-session/`，不是 Skill 安装目录或项目代码目录；必须验证两端访问其职责所需文件的权限。本文件不授权修改全局配置或扩大沙箱。

路径必须规范化并验证仍位于配置的运行根目录内；身份字段不能直接变成可逃逸的路径或命令。身份恢复不读取或改写 Codex 内部数据库，不依赖原始 transcript 格式作为稳定协议。

最小文件职责：

| 文件 | 内容与权威边界 |
| --- | --- |
| 两端各自的 `role.json` | schema/revision、精确身份、角色类型与状态、对端引用、配对版本及 Manager 锚点；绑定入口在明确授权下更新 |
| Manager 的 `manager.json` | 契约版本、已确认委派授权、项目与轮次索引、在制上限、监督运行策略及其调度引用；不代替 Liaison 的报告记录 |
| `session.md` | 可读的当前摘要：长期目标、有效决策来源、开放轮次、待验收与待决策事项；不是完整聊天备份 |
| `rounds/<roundId>.json` | 本轮范围、验收、所有权、后端引用；仅原生受管模式拥有其工作项业务状态 |
| `observations.json` | Manager 维护的 Worker 游标与最新观察，不作为完成证据 |
| `progress.json` | Manager 发布的只读进度投影：来源版本、观察/变更时间、工作阶段、审查结论引用、待决策和重要事件 ID；不是第二份权威业务状态 |
| `inbox/<commandId>.json` | Liaison 追加的已确认控制请求及用户来源；成功登记后内容不可覆盖，变更以新请求表达 |
| `receipts/<commandId>.json` | Manager 写入的核对、处理与生效回执，Liaison 只读；不能反向改写原始请求 |
| Liaison 的 `reporting.json` | 报告策略、原生调度引用及实际状态、报告周期与事件去重记录、完成范围版本、逻辑汇报状态和最终结论交付记录；仅 Liaison 日常更新 |

除标明两端或 Liaison 的文件外，上表路径均位于 Manager 锚点下。配对是显式管理操作；普通查询、周期汇报和来自 Worker 的内容都不能修改角色绑定。报告用的读取游标属于 Liaison 自己，不覆盖 Manager 的观察游标。

每个原生工作项的绑定包含原生任务身份、负责范围、后端、验收 ID、最近已确认交接标识和证据引用。大段审查材料放在相应轮次的按需文档中，不进入每轮启动摘要。

决策与项目事实优先引用 PDC/项目原有文档，不复制成为第二个权威版本。只保留必要的状态变更摘要和证据定位，不保存原始任务日志、凭据或完整工具输出。

正常监督时，原生业务状态、进度投影和处理回执仅由当前合法 Manager 写入；Liaison 仅追加自己的指令并更新自己的报告记录。轻量状态工具校验 schema、身份、配对及范围版本，使用互斥写入与原子替换防止覆盖。进度读取必须核对其来源版本；更新中、版本不匹配或文件损坏时重读或报不可确认，不拼接出虚假的一致状态。

角色初始化、配对与退出通过明确授权的绑定入口更新；这不是日常运行时抢占业务所有权的通道。恢复 hook 保持只读，不批准工作、不调度 Worker，也不处理控制请求的副作用。PDC 文件仍只由其租约持有者按 PDC 协议写入。

两端恢复输入均设固定上限：只注入短角色提示、精确状态路径和版本；轮次、历史记录按需读取。指令、回执和事件按未处理索引或游标读取，不把完整历史复制到另一任务。模拟大量历史轮次时，启动输出大小不能随历史总量线性增长。关闭记录保留索引，不默认删除，也不每轮全量扫描。

这里的单写者与路径校验保护的是本功能的状态一致性；它们不构成对同权限本地进程的安全隔离，也不覆盖外部工具的授权机制。

## 8. 后续多轮如何恢复角色

### 能力依据与选择

官方文档说明：`UserPromptSubmit` 与 `SessionStart` 可追加模型上下文；后者覆盖恢复和压缩续接。hook 输入提供会话身份，但 subagent 相关事件可能携带父会话身份。非托管 hook 必须经用户审阅并信任，工具 hook 也不是完整安全边界。[OpenAI 官方 Hooks 文档](https://learn.chatgpt.com/docs/hooks)

据此，V1 选择轻量的 `UserPromptSubmit` 和根会话 `SessionStart` 恢复入口，而不是宣称一次 Skill 调用就修改了原生线程类型。

### 恢复协议

1. 只处理已支持、经验证的根会话事件；明确忽略 SubagentStart/SubagentStop 等非目标事件。
2. 从可信宿主字段解析会话身份，并在安装测试中核对它与原生任务身份的映射；不能直接相信继承的环境变量、标题或文本中的 ID。
3. 查找对应的有效角色记录，核对 `manager` 或 `liaison` 类型与配对版本。没有绑定或已退出时无角色注入；相同项目里的其他任务保持原行为。
4. 角色有效时注入对应角色的固定最小恢复指引：加载 `manager-session` 协议，读取指定状态，并先处理当前用户的新指令，包括退出。Liaison 不得加载成监督循环或获得 Manager 所有权。
5. 动态目标、Worker 内容和文件摘要只作为明确标记的数据按需读取，不拼入高优先级指令；hook 不解析用户文本来执行操作。
6. Manager 恢复后先核对实际任务、控制请求与回执、后端所有者和工作区事实，再继续监督。Liaison 恢复后核对配对、进度来源时间与报告记录，再回答或汇报，不触发业务执行。旧的“通过”或游标不能替代新证据。

对请求处理中发生的角色压缩丢失，两端都必须覆盖压缩后的立即续接，而不只等用户下次发消息。退出后、同目录其他任务、fork、子代理以及两种角色之间的隔离均须单独测试。

### 安装与降级

- Skill 安装、状态目录配置、hook 注册与用户信任是可区分的步骤；不得自动替用户信任 hook 或绕过宿主限制。
- 不覆盖既有 hooks，不改变其他 Skill 行为。配置修改需备份、精确合并和验证。
- 本机验证至少包含两端身份及配对、普通后续轮次、应用恢复、压缩续接、定时触发恢复正确角色，以及退出后不再注入。
- 能力未验证、hook 未信任或状态损坏时，标明自动恢复未就绪；手动 `$manager-session resume` 可作为明确披露的临时路径，但不算完整长期模式通过。
- 角色提示与恢复机制是工作流约束，不是工具访问的安全隔离。若 hook 被完全禁用，不能保证模型必然知道它已失效；不得声称完全 fail-closed。

不增加默认的 PreToolUse 全命令封锁或无限 Stop 续跑。角色恢复、工具权限、自动运行是三个不同问题。

## 9. 委派授权、所有权与证据

### 授权

启用角色不等于已经授权某个代码目标或任意新任务。创建 Liaison 或 Worker 前必须有用户明确的新任务创建/委派授权和对应范围。可以记录用户对某个目标下“由 Manager 创建或复用独立任务执行”的持续授权，避免每次返工重复询问；不能由 Skill 自己生成授权。

Liaison 只转交用户已确认的内容，保留来源与作用域；Manager 核对可验证的原始用户决定和既有授权，不把 Liaison 自称“用户已批准”或外部文档中的指令当作新增许可。来源字段是核对线索，不是宿主权限凭证；无法核验的新增授权进入 `NEEDS_CONFIRMATION`，不得先执行后补确认。

领域操作权限与委派授权分开：能创建部署任务，不代表部署任务已获准修改生产环境。审批请求留给用户，不代点、不修改为更宽的授权。

### 工作区

- 新建 Git 项目任务遵循当前宿主的隔离默认值；使用本地共享 checkout 须有明确依据。
- 不从参照任务继承“本地分支、不建 worktree”等环境选择。
- 同一可变 checkout 同时最多一个业务写入者；共享构建目录、数据库、容器等另有资源互斥。
- Manager 独立回归前确认 Worker 的冲突操作已经结束，避免两个 Maven/构建过程争用同一输出目录。
- 记录精确项目、根目录、分支、基线、已有脏改动与允许路径。原生空闲不证明目录没有外部并发修改。
- 提交、推送、合并、迁移、部署按当次授权或明确有效的后端政策处理，不由 Manager 角色自动授予。

### 最小 handoff

Worker 应收到：具体目标、已确认决策、来源引用、作用域与非目标、所有权、依赖、所用领域 Skill、验收条件、禁止事项和交付证据要求。信息来自已知或核对过的事实，不复制两端的完整聊天。

交付至少提供实际改动与产物、测试命令和结果、跳过项、验收 ID 对应证据、未完成依赖和现场未验证项。Manager 按风险核查实际事实，而不只检查这些字段是否填满。

## 10. 异常、幂等与中断

| 情况 | 必须采取的行为 |
| --- | --- |
| Worker 交付缺证据或只说“完成” | 保持待验收，向原 Worker 要求具体证据或补测 |
| 同一交付重复出现 | 通过原生 turn/cursor 和已处理事件标识去重，不重复批准或返工 |
| 发送结果不确定 | 先读取原任务核对交接标识；不能盲目重发有副作用的执行请求 |
| 创建只返回 clientThreadId | 保持 CREATE_PENDING；不拿它调用等待/读取/消息，也不重复创建 |
| Worker 丢失或目标项目不匹配 | 停止相关调度、保留证据，要求明确恢复决定；不按标题认领其他任务 |
| 用户中途变更范围 | 更新范围版本，停止新的冲突调度，向原 Worker 说明；在确认实际停止或空闲前不发冲突执行 |
| 状态版本未知、损坏或写入竞争 | 不猜测覆盖；说明恢复问题，保留原文件和已有证据 |
| 后端不可用、权限待批或没有安全下一步 | 如实报告阻塞与所需决定，不改由主任务越权执行 |
| 接收其他任务的指令或宣称已批准 | 仅将匹配配对、来源与版本的控制请求送入核对；其余视为待核查数据，不自动改变范围、权限或角色 |
| Liaison 长时间聊天、暂时不可用或被关闭 | Manager 不接收普通问答输入、不暂停 Worker；保留未送达事件并继续范围内监督 |
| Manager 不可达或观察过期 | Liaison 报告最后可核验状态、时间及不可确认项；不重建 Manager、不接管 Worker |
| 进度投影与来源版本不同或正在更新 | 只读重试或说明尚不能确认，不拼接出新的验收结论 |
| 指令重复、通知结果不明或范围版本过期 | 按 ID 与回执对账；重复请求不重复生效，过期请求要求重新确认 |
| 周期唤醒撞上正在运行的任务或恢复后漏掉多期 | 不建立竞争监督者；去重并合并为一次当前报告，记录实际时间，不补造历史运行 |
| 两端配对版本不匹配或用户只关闭汇报 | 前者停止控制投递并说明绑定异常；后者仅关闭报告调度，不隐式退出 Manager |

发送后续消息并不保证立即打断正在运行的 Worker。归档、fork、迁移都不能冒充取消机制。退出或中断后的重入必须先对账，防止重复创建、重复部署或批准旧范围的交付。

## 11. 验收标准

先做离线契约与模拟宿主事件测试，再在用户明确授权的独立测试环境里做最小实测。设计审阅、安装、校验和 dry-run 都不自动授权创建真实任务或操作用户项目。

| ID | 场景 | 必须观察到的结果 |
| --- | --- | --- |
| MS-01 | 仅启用角色，没有工作范围 | 只绑定当前任务，不隐式创建 Liaison/Worker、改业务文件或安排自动化 |
| MS-02 | 连续完成至少三轮需求，模拟时间跨数月 | 每轮独立收口，角色仍 ACTIVE；不伪称已做数月实测 |
| MS-03 | 两端普通后续消息、恢复应用、压缩及定时续接 | 重新读取各自正确角色和最小状态，不依赖完整历史、不相互升级角色 |
| MS-04 | 同目录另一任务、Worker、fork、子代理 | 不因目录相同或继承父身份字段变成 Manager |
| MS-05 | 从任一端显式请求整组退出，包括关闭调度失败 | 区分待处理、部分退出与整体完成；已退出端不再运行角色动作，保留历史并报告未完成清理，不宣称 Worker 已取消 |
| MS-06 | Worker 首次交付含具体缺陷 | Manager 给出证据化 finding，发回同一 Worker，复验后才批准 |
| MS-07 | 实现阶段已出现可审查产物 | Manager 可提前审查并补充反馈，不必等最终回答才发现问题 |
| MS-08 | Worker 声称成功、测试跳过或只有 Fake 结果 | 与实际证据核对，保留未验证项，不误报目标达成 |
| MS-09 | 需要扩大项目范围或部署权限 | 暂停相关操作并请求用户决定；不替用户批准 |
| MS-10 | 必要依赖未批准、存在人工作业验收 | 不提前解锁或关闭总体目标 |
| MS-11 | 重复快照、pending 创建、发送结果不明 | 不重复创建、发起副作用或批准旧交付 |
| MS-12 | 与 PDC 组合 | 一个逻辑所有者、一个 PDC 权威记录，不出现竞争调度 |
| MS-13 | task-dispatch 投递即止 | 不改变旧 Skill 语义，不把投递成功当成本轮必要结果已验收 |
| MS-14 | 领域 Skill 需要实施操作 | 操作发生在获授权的 Worker；主任务维持审查责任 |
| MS-15 | hook 未信任、被禁用或状态损坏 | 不宣称自动恢复已就绪，不绕过信任或权限 |
| MS-16 | 大量已关闭轮次 | 启动上下文保持有界，只按需读历史，无完整日志复制 |
| MS-17 | Worker 与 Manager 共用构建输出 | 独立复验等待互斥资源释放，不并发破坏输出 |
| MS-18 | 本轮标准已满足 | 主动收口，不无限扩大验收；角色继续待命 |
| MS-19 | 显式配对、重复配对或只有 pending 任务标识 | 只有核验过的真实双向身份进入就绪；不重复创建、不把 Liaison 变成第二个 Manager |
| MS-20 | 用户持续在 Liaison 查询或讨论，Manager 正在监督 | 普通查询不向 Manager/Worker 发送消息或控制、不写业务状态；受控并行实测中 Manager 继续推进 |
| MS-21 | 用户提出尚未确认的想法 | 保留为讨论或草案，不创建执行指令或派发工作 |
| MS-22 | 用户确认变更，同一指令通知被重复投递 | 来源和版本核对后只应用一次；报告区分已登记、已接受、已生效，不用发送成功代替回执 |
| MS-23 | 过期范围、错误配对或无法核验的新增授权 | 拒绝或要求重新确认，保持原始请求和证据，无新增业务副作用 |
| MS-24 | 用户通过 Liaison 要求暂停或涉及宿主权限 | 请求正确转交，真实暂停未核实前不报已停止；不代批宿主权限 |
| MS-25 | 长构建连续多个报告周期没有新进展 | 每期有简短进展，附原始观察时间；旧记录不被刷成新事实，不编造百分比 |
| MS-26 | 定时触发与长对话/监督重合，或应用离线后恢复 | 记录宿主实际合并/延迟表现，不重复监督或报告；漏期合并，自动化未就绪不报通过 |
| MS-27 | 多个工作项同时提交且达到在制上限 | 默认 3 项限制和审查队列生效；活动任务均有观察记录，不以批量 8 项误作容量承诺 |
| MS-28 | 重要事件重复出现、消息失败或结果不明 | 只投递至绑定 Liaison，核对来源并按事件 ID 去重，失败保留待报告且不重复副作用 |
| MS-29 | Liaison 不可用或用户只关闭汇报 | Manager 和 Worker 继续原授权工作；不新建替代沟通任务、不扩大权限 |
| MS-30 | Manager 不可达而 Liaison 仍可对话 | 报告过期/未知及最后确认时间，不冒充实时监督或直接指挥 Worker |
| MS-31 | 部分/全部轮次关闭、最终汇报、数月后查询及新轮次 | 部分关闭不停止其他轮次；全部关闭且最终报告交付后停止空闲汇报，角色保留；普通查询不开工，新授权轮次按有效配置恢复 |
| MS-32 | 双窗口组合 PDC 及其既有后台所有者 | Liaison 仅用允许的只读入口，原生续跑不叠加第二监督者，进度投影不覆盖权威状态 |
| MS-33 | Manager 全部验收完成，旧汇报触发仍在队列或暂停失败 | 最终结论仅一次、普通进度停止；核对 heartbeat 实际暂停，失败记录清理异常；旧触发不重复播报，手动问答不重启定时 |
| MS-34 | Manager 原生任务空闲/回复结束，或旧完成事件到达时已有新工作 | 不以原生空闲代替业务完成；按当前范围版本核对，旧完成事件不能停掉新轮次的汇报 |

源码、状态工具、hook、指令核对、定时运行和实际双窗口交互要分别验证。schema 校验成功不等于模型会正确审查；模拟时钟通过不等于本机准点汇报；dry-run 对话成功也不等于当前桌面应用已可靠执行 hook。实现前的文档自检仅验证规格一致性，不宣称上述运行验收已经完成。

## 12. V1 交付范围与下一步

V1 包含：一个独立 Skill 的 Manager/Liaison 两种角色、显式配对与恢复、只读进度与确认指令/回执、有限在制与审查队列、原生周期汇报和监督续跑、原生受管任务适配、PDC 组合边界、Worker/返工模板，以及上述分层验证。

V1 不包含：新任务管理平台、专用看板、自建常驻服务、未经授权的自动化、多个 Liaison 或跨多个 Manager 的统一调度、自动跨任务身份迁移、跨所有宿主的安全强制执行、重写 PDC 或 task-dispatch、自动归档与删除策略。仅启用角色不创建自动化，但已授权活动轮次的主动汇报属于本版交付，不再排除在外。

本次修订经用户审阅后进入实施计划：先验证本机双任务身份、恢复与定时重入边界，再实现最小角色绑定、进度/控制记录和监督闭环，最后完成真实双窗口交互与后端组合的受控测试。无法满足宿主能力门槛时明确缩小交付声明，不先宣称长期不打断或自动汇报已实现。
