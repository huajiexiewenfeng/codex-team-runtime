## 1. 要解决的问题

将 Manager 在派发、接收提交、记录验收决定时反复完成的参数拼装、协议查阅、编号与时间格式处理交给确定性程序。Manager 保留需求、拆分、授权判断、独立验收和返工决定。

优化对象是**团队协作协议的调用成本**，适用于编码、产物构建、文档研究及跨项目协作。业务工具自身的耗时和参数错误由各自项目解决，不进入通用引擎。

成功必须同时满足：

1. Manager 的机械调用错误、查实现修参数和相关模型往返减少。
2. Worker 不增加启动/恢复调用、必读材料、字段或汇报动作。
3. 提交、收到通知、开始审查、业务验证与最终批准仍可分别核验。
4. 其他团队的派发、收件、返工、完成发现与恢复不退化。

## 3. 第一批方案：两项改动，共用现有核心

### P0-1：Manager 的结构化操作入口

**建议首批提供 Runtime 命名请求入口，通过现有 shell/functions.exec 调用；暂不新增全局 MCP 工具。** 示例命令名 `manager-request` 只是待实现名称，不是当前可用命令。

理由：用户需要的是减少模型拼装与返复试错，而不是增加一种工具。CLI 可以同样调用确定性核心，并避免新工具名称/schema进入所有 Worker 的工具目录。未来如需要 MCP 绑定，复用同一入口，另测工具目录成本，不并入本批。

职责映射：

| 逻辑动作 | 输入中的业务信息 | Runtime 的确定性工作 | 明确不代替的判断 |
| --- | --- | --- | --- |
| enqueue | 精确团队/轮次/任务/Worker、原始 brief 引用、必要任务属性 | 身份与版本检查、构造既有 enqueue 事件、记录一次结果 | 是否拆任务、分给谁、范围与验收标准 |
| receive | 精确 task/submission/notice；已有 inbox 模式下的真实 claim/owner 上下文 | legacy 路径复用 receiveSubmissionNotice；queue_first 路径复用 start_review | 不把“已收到”变成“验收通过”，不自动创建 consumer 或领取其他任务 |
| record_decision | 当前提交、已有 review、明确 approve/rework、Manager 原文结论及证据引用 | 校验精确关联、版本和状态，再记录既有决定事件 | 是否达到验收要求、测试是否充分、是否允许安装/部署 |
| status | 精确操作/任务标识 | 查本次操作是否落账，返回紧凑引用 | 不推断通知已送达，不重新执行，不全量展开历史 |

派发继续使用既有 E04。进度继续调用 `progress_summary(task_id)`。注册/成员管理仍由 `manage` 负责，不把 task 操作塞入 Registry 管理协议。

模式或已安装能力无法确认时，返回明确的能力/模式未知结果，保留任务现状；不自行选择另一条路、不启用收件箱、不临时升级安装。源码存在但安装缺失的能力不能被模板直接调用。

#### 请求与错误契约

- 入参使用封闭的命名字段，JSON Schema 与运行时校验来自同一份定义；不再让 LLM 猜 CLI 参数顺序。
- Manager 的既有上下文传入已核对的身份、目标和 `expectedVersion`；程序不擅自以“最新版本”替换其决策依据。
- 事件 ID 由程序根据稳定操作身份生成；记录时间由程序写规范 UTC 毫秒时间。外部观察、命令执行与提交的原始时间另按原证据保留，不改写为当前时间。
- 固定流程首次生成并保存稳定 operation_id 与原请求，重试复用原请求。原请求及正文引用保留在本次任务已有证据范围内，不新增全局数据库，不存对话过程。
- 优先用已有事件、操作记录及不可变引用核对同操作同输入。已有 E04/E05 幂等记录直接复用；没有充分证据时返回“需核对”，不能仅凭相同 ID 声称成功，也不能补发事件。
- 如果实现核查发现必须新增持久化结构，先列出字段、大小上限、旧版本读写兼容与回退办法，回到设计评审；不得顺手扩成第二套任务账本。
- 非法字段返回字段路径、原因、合法值或最小例子、是否已写入、精确操作引用与下一步允许动作。SDK/CLI 包装也须保留这些信息，不能只吐出一段堆栈。
- `reason` 从现有 REASONS 读取；Manager 模板根据真实触发点传值，不把所有原因改成 manual 来消除报错。错误示例不是自动修正授权。
- 版本冲突只返回必要冲突信息；Manager 核对变化后决定是否构造新请求。参数修正与效果未知的重试必须分开处理。
- 正常返回只含 task/submission/operation/event 引用、版本、结果和必要错误；不返回整份 state、Worker 对话或历史证据正文。

### P0-2：Manager 固定宿主流程

固定流程在 Manager 已经进行的操作中传递值、调用程序、筛选输出；不新增每次启动或恢复的准备回合。

**派发：**

1. Manager 确定任务卡、Worker、写入范围、验收标准和授权验证要求。
2. 固定流程按既有规则冻结原始材料、入队并请求 E04 prepare；每步使用上一阶段真实返回的精确引用。
3. 仅 fresh prepare 返回 `sendNow=true`，且已有用户授权足够时，由宿主执行一次真实发送。
4. 将真实宿主结果登记到同一 attempt；unknown、denied 或输出丢失按原规则核对，不自动重发。

身份/idle检查、busy保护、依赖及跨项目工作区核对沿用现有流程。它们不能因“固定流程”被跳过；也不能为使用模板额外增加 Worker 的身份回执。

**接收与验收：**

1. 用 supervision-plan 的 taskChecks/pendingSubmissions 找待办；具体进度与验收读取精确 task_id 的摘要。
2. 按实际通知模式接收精确提交，保留已存在的 inbox owner/claim 约束。
3. Manager 根据任务卡、diff/产物及证据独立判断，运行已获授权的复验。普通验收不读取 Worker 执行对话。
4. Manager 明确给出 approve/rework、结论与证据引用，程序登记决定。
5. 已启用 queue_first 时，再用这个真实决定事件 resolve 对应项；其他团队不执行该步骤。

固定流程可在一次 functions.exec 调度中完成多个已确定步骤；**不承诺跨 Runtime、文件、宿主发送与业务验证的原子事务**。任何部分完成都返回分阶段事实和可恢复引用。

审查产生新判断、参数冲突或需要授权时，仍由 Manager 处理。工具次数、模型调用次数与代码内部步骤分别计数，不以包装成一次工具调用冒充消除了所有成本。

### 语义、权限和业务边界

| Runtime 负责 | Manager/Worker 或项目工具负责 |
| --- | --- |
| 格式、枚举、身份与任务绑定、版本、去重、状态转换合法性、关联引用、紧凑输出 | 需求、任务划分、业务正确性、证据充分性、独立验收与返工判断 |
| 原样保存 brief、summary、决定与证据引用 | 提供真实原文、真实产物、命令结果和授权依据 |
| 明确记录 local event / host accepted / reviewing / approved 的差别 | 项目工具自身的批准、构建、部署、现场验证 |

Runtime 不压缩、改写或“补全” LLM 原始业务语义；仅规范其自有 envelope。正文保持字节/哈希可核对，过大时使用已有不可变引用或明确报错，不静默截断。

只存在证据路径不等于命令确实执行成功，身份字段/hash也不是额外认证。通用入口不能替代宿主权限、制造人工批准或为项目工具生成不存在的审批来源。

服务名称、镜像类别、版本号、归档名、业务命令和 Harness 特定状态留在任务卡/项目配置。没有 PDC 或 Harness 的团队也能正常使用通用流程。

## 4. 首批明确排除

不修改 Worker 提交格式、通知 prompt、启动/恢复和 ready 规则；不增加 Worker read、阶段消息、日报或计时上报。

不切换 E03/E04/E05 模式，不自动迁移历史，不全局同步 main，不调整模型，不新增 timer/后台扫描，不自动安装、部署、合并或推送。

不修改构建/打包/SQL/Linux 校验等业务实现，也不放宽独立审查。Manager 默认不读 Worker 对话和等待结果投影继续沿用现行规则，不在本批重复扩建。

## 5. 跨团队验收矩阵

### 5.1 离线通用矩阵：开发后的必验项

离线测试使用隔离 fixture、fake host 和故障注入，不改真实团队。fake host 通过不等于实际宿主投递已验证。

| 编号 | 场景 / 组合 | 必须满足的验收条件 |
| --- | --- | --- |
| G01 | 代码修改、产物构建、文档研究；各一次直过闭环 | 同一协议完成 enqueue/dispatch/submit/review/approve；无业务名称分支；未配置 Harness 的任务不被要求 Harness accept |
| G02 | 一次返工、两次提交 | 两次提交身份独立；决定只作用于指定的当前提交；旧 notice/旧决定不能批准新提交 |
| G03 | 多 Worker 并行、不同项目；分别有/无 PDC | 精确任务/工作区/依赖保留；各任务独立审查，集成验收仍由 Manager 作出；不强制共享项目或 PDC |
| G04 | Worker 忙碌、任务排队、依赖未就绪 | 不打断当前 Worker，不绕过占用与依赖保护，不把排队记成开始执行 |
| G05 | legacy/observe 与已启用 queue_first | 原路径均可用；不初始化/切换 inbox；queue_first 失败无 native fallback；resolve 引用真实已存在决定 |
| G06 | 同请求重试、同 ID 改输入、宿主输出丢失 | 已证明的同请求最多一份业务事件；异输入拒绝；unknown 保持 unknown；没有新发送许可 |
| G07 | 版本竞争、同时收到多个提交 | CAS 冲突可修正且不自动选新版本；不误收或错批另一任务；每个提交可继续处理 |
| G08 | 写入前失败、事件已落账但返回丢失、决定成功但 inbox resolve 失败 | 明确已完成阶段；按原操作查询恢复；不重复决定、不恢复旧 state、不取消其他在途工作 |
| G09 | 非 Manager、错团队、旧绑定、缺授权、跳过 review | 原身份/范围保护不弱化；submitted 不能直接 approve；不从对话正文制造授权 |
| G10 | reason、时间、必填字段或位置错误 | schema 与程序一致；字段错误在业务写入前返回有界可修正信息；当前时间与外部证据时间分开 |
| G11 | 长摘要、大 diff、中文/换行、历史量增加 | 不改业务正文；错误和正常返回有界；不展开全量历史；不存在默默截断后照常批准 |
| G12 | Worker/Liaison 启动、恢复、旧 receipt 和旧任务 | 与当前安装基线对照，必需调用/输入/返回/读取清单不增加；旧 receipt 与进行中任务仍可用 |
| G13 | 执行结束但遗漏提交、阻塞、原生结构未知 | 既有完成发现与诊断路径保留；不因新入口只看提交而漏发现结束；unknown 不授权读整段对话 |
| G14 | 新旧 Manager 调用方式交错 | 旧 CLI/提交仍可识别；旧写入器不理解数据保护时拒绝混用并说明；不能形成双重派发/批准 |
| G15 | 已有通知恢复与 prompt | 原通知内容、hostRequest 校验与去重保持；本批无文案引起的恢复比对失败 |

G01/G02/G04/G06–G10 至少分别覆盖 legacy 路径及 queue_first 路径；G03 至少覆盖双 Worker 和跨项目组合。不是把一组 happy path 复制成三个团队名。

Worker 契约“不增加”须对照实际安装基线和候选分别验证，不能仅比较新分支内两个相同实现；同样核对全局 MCP 工具目录没有新增 Manager 工具或 schema 扩张。

## 6. 同口径指标与判定

观察单位是精确任务和精确操作；原有协商税分类继续使用 dispatch/clarify/execute/submit/review/rework/status_sync/recovery/other，不因优化改名规避分母。

| 指标 | 口径 | 通过/判断标准 |
| --- | --- | --- |
| 协议错误与修复往返 | 字段/枚举/位置/格式错误；因此查实现、重试的模型调用数 | 离线合法请求无错误；自然样本没有新的系统性错误，已有机械错误减少才算收益 |
| Manager 机械模型调用 | 分列派发准备、收取提交、决定登记；一次 exec 内多个工具另计 | 与同团队同类 baseline 比较；不预设全部闭环必须一次模型调用 |
| 状态及对话读取 | 精确 task 摘要、普通/诊断 Worker 对话读取、wait投影分别记录 | 普通进度不读执行对话；诊断保留理由和最小切片；不增加轮询 |
| Worker 启动/恢复税 | 必需 MCP/宿主调用、必读材料、请求/响应字节与实际耗时 | 契约新增动作/字段/必读文件为 0；字节、调用和共享工具目录作基线差分；实际毫秒/Token缺测写unknown |
| Runtime 单操作耗时 | 隔离同规模 state、同环境重复测量，列原始样本与中位数；操作与文件 I/O 分开 | 新开销单列；明确可归因的额外扫描或新增等待不接受；小样本不能冒充稳定 p95 |
| 任务时间线 | 派发决定→host accepted→Worker开始→submit→review→decision；准备、验证、等待单列 | 不把整段空隙都算 Runtime；缺边界写unknown，不估算补齐 |
| Token/费用 | Manager、Worker、Liaison分开；cached/uncached input、output；模板加载成本计入 | 有实测usage才能计算；不同模型/缓存/任务不直接算节省率；不以字节换算Token |
| 验收质量与恢复 | review是否存在、独立证据、错误批准/重复执行、返工及漏报 | 任一跳过审查、错任务或重复副作用即失败；返工率本身不等于质量退化，需核对原因 |

“准备/收口各 1–2 分钟”可以保留为方向，不能作为跨所有任务的硬承诺。不能把各项理论节省相加。

方案收益要求同时报告 Manager 节约与新增程序/模板开销；不能将额外步骤转嫁给 Worker 后宣布协商税降低。

## 7. 进入开发、安装与观察的顺序

| 阶段 | 产出与完成条件 | 权限边界 |
| --- | --- | --- |
| D0：方案确认（当前） | 本文、能力缺口、验收矩阵与回退条件 | 只改文档，现有安装不动 |
| D1：候选开发 | 经用户确认后由独立 Worker 完成两项 P0；Manager 审查；先核对安装/源码能力及请求到现有事件的字段映射 | 独立候选工作区，不改运行团队；需要新增状态结构、Worker协议或全局MCP时先回到设计 |
| D2：离线验收 | G01–G15、契约/工具目录差分、故障恢复与回退演练；测试日志本机保存 | 仅 fixture；不是业务通过或安装授权 |
| D3：安装提案 | 给出实际差异清单、原/新哈希、依赖、在途兼容、备份和经演练的回退方式 | 另获用户确认后才安装；不借本批全量升级main或自动迁移E05 |
| D4：自然观察 | 按R/F/U各自切点观察至少两轮；非目标路径行为保持；记录未覆盖项 | 安装若共享则如实说明影响范围，不能声称“只给R安装”；不自动切模式 |
| D5：收口决定 | 逐团队报告行为、质量、调用成本、unknown与反例，再决定保留/修订/回退/合并 | 两轮不是自动合并开关；以用户确认决定为准 |

实现时先完成 P0-1 的契约/核心复用，再接 P0-2 的 Manager 调用模板；一起离线交付为一个候选。每次自然观察只改变这一项协作入口，不同时调整模型、Worker流程或业务引擎；确有外部变动则记录混杂因素。

## 8. 回退与停止推广条件

### 8.1 立即停止候选新操作的条件

任何一个团队或离线矩阵出现下列情况，均视为通用候选未通过，不能因R更快而豁免：

- 错派、重复发送、错任务验收、跳过review、证据或业务正文被改写。
- 未知投递自动重试、queue_first失败转原生发送、忙碌Worker被打断。
- 在途任务无法恢复、已存在的提交/阻塞/结束发现漏报。
- Worker新增启动/恢复调用、必读材料、回执字段或强制通知步骤。
- 未授权切模式、扩大写入范围、伪造批准来源，或新旧写入器保护不一致。
- 新入口对某一任务类型依赖业务专属字段，导致无Harness/PDC的团队不能正常工作。

同口径出现可归因的Manager机械调用增加、持续参数错误、明显新增I/O或等待，则停止推广并分析；未取得可比样本是“待结论”，不自动判失败或收益为零。

### 8.2 回退步骤

1. 停止 Manager 发起候选的新操作；不向已执行的 Worker 发取消/重启消息，不修改其任务状态。
2. 保存精确操作/attempt/事件引用，区分未写入、已写入、宿主accepted、unknown及决定已记录但resolve未完成。
3. 使用理解当前记录格式的读取与恢复入口对账。只回退调用方式不代表可以丢弃在途记录；unknown仍不允许重发。
4. 核对实际安装清单、哈希及后续并行改动。恢复的是本候选替换的代码/规则，不是旧团队state、Registry、通知账本或业务产物。
5. 若所有持久化数据保持旧版兼容，按已演练备份恢复；若旧版不理解新增记录/保护，保留兼容reader/result登记与保护，采取停用入口或前向修复，不能直接换旧二进制继续写。
6. 在隔离副本复验读取、在途恢复和旧入口后，按用户确认恢复正常Manager操作；原记录、失败证据和样本全部保留。

此前三文件召回补丁的备份只覆盖那次补丁，不能充当未来本候选的完整回退包。本批也不执行该旧备份回退。

回退代码不逆转已经批准、已经执行或已经投递的业务事实；不恢复旧state覆盖新进展，不删除文件或清空队列。

## 9. 待确认的执行边界

建议确认以下三个决定后再开发：

1. 首批只做 **Manager结构化Runtime入口 + 固定宿主流程**；复用E04/E05，不改Worker协议、业务引擎和通知prompt。
2. 首批通过现有shell/functions.exec接入，**不新增全局MCP工具**；既有MCP仍承担派发、摘要等能力。未来增加MCP绑定单独评估全局上下文成本。
3. **跨团队非退化优先于单队提速**：离线矩阵先通过，再经明确安装授权，分别观察R/F/U两轮；无样本保持待验收，重大问题停止候选新操作并按上述条件回退。

仍待实测：真实模型调用与Token收益、各团队自然采用、共享文件锁/I/O开销，以及异构模型和任务混杂下的效果。代码对格式和状态的检查不能证明业务验收一定正确。
