# 当前登记任务锚点：最小方案

日期：2026-11-09。状态：提议已归档，尚未实施。只讨论通用协作层；本次不修改 Runtime、Skill、安装或运行团队。

## 问题与证据边界

已观察到 Worker 正确开始新任务，在上下文压缩后转向历史事项。角色恢复成功不保证当前业务任务选择正确。未获得压缩摘要正文，不能判定摘要错误、模型选择错误或优化回归。

本地只读抽查三个正式团队的 22 个 active Worker：13 个有一个非 queued/approved/cancelled 的占用任务，9 个无占用，未发现多个占用。这是 2026-11-09 当时快照，不是永远唯一或最新用户意图正确的保证。事故任务的唯一占用、轮次绑定、E04 原操作及冻结任务卡哈希均有对应证据。原始任务卡约 10.7 KB，不应默认全部返回。私有身份和业务日志不上传。

## 目标与存储

从现有台账生成只读投影，不新增 current-task.json，不建立第二份需要同步的任务状态。Manager 定义任务，原派发和状态变更程序维护事实。程序不改写、总结或推断业务语义。

输出：定位结果（唯一、无占用、冲突、不可用）、team/round/task、成员绑定版本、台账原标题、任务状态、原派发及冻结任务卡引用、阻塞/撤销/交接/投递风险、快照版本。响应设长度上限；不返回历史任务列表或自动生成下一步动作。

## 最小实现落点（候选，未开发）

1. 在现有 Registry adapter 校验链内复用已读 state 和已验证 E04 对象，生成 Worker 投影。不得再次扫描并加载一遍相同对象；调用边界需要让现有校验结果可以复用。
2. Python TeamRegistry.read 在已有响应中附带投影；复用原 Node 调用，不另开进程、不重复读取台账。当前配置安装入口已具有 state 读取与 adapter inspect 路径。
3. team-context 规则及有界投影调用端保留并解释该字段；不要求 Worker 多调用恢复工具，不增加确认回执。
4. 首批不改提交接口、任务状态机或增加提交版本参数。已有提交检查负责人、绑定及可提交状态。Manager 多任务调度不套用 Worker 唯一占用算法。

## 解释规则

- 唯一登记不等于最新意图或执行授权；台账陈旧可能仍唯一。
- queued 不自动执行；submitted/reviewing 不自动重新开发或提交；无占用不复活历史事项。
- executing 可能仍有阻塞报告或投递未知，必须保留风险，不能直接返回“继续执行”。
- 旧摘要与登记任务不一致时，核对精确任务卡引用，不继续无关历史动作。
- 用户最新明确指令优先；与台账不一致时识别差异，不能用旧任务卡覆盖同任务后续补充、暂停或限制。
- 旧派发缺少冻结 brief 时如实标注引用缺口，不猜版本；绑定冲突或多个占用返回冲突。
- 锚点是读取时快照，不是锁或长期授权；不因其他任务推进导致全队 version 变化就判本任务失效。

## 成本与触发

随已有 onboarding/resume/post_compaction 等角色读取返回，不新增 Worker 启动或恢复调用；原派发、提交与结束自然改变投影，无独立锚点写操作。正常工具、shell 和文件读取不额外查锚点。

验收：模型调用数不增加、Node 子进程数不增加、台账与 E04 对象不重复读取校验；响应长度有界。读取与响应仍有增量成本，离线记录字节数和耗时，不承诺零 Token 或固定节省比例。冲突时按需读取任务卡属于纠偏成本。

若压缩后没有发生已有恢复调用，MCP 不会自行出现；本方案不能拦截直接 shell，也不能恢复只存在于对话里的最新指令。暂不引入 Hook、定时器、工具拦截或自动会话轮换。

## 验收与后续观察

离线覆盖：唯一执行、仅排队、待审查、阻塞报告但状态 executing、投递未知、撤销/交接、旧绑定、多占用、无 Runtime 关联、旧派发无 brief、对象缺失或损坏、旧摘要与新任务矛盾。保持角色恢复原有校验和拒绝边界。

真实任务观察恢复后的第一步是否服务当前任务、是否误执行旧动作、是否以旧结果冒充交付；安装、调用采用、漂移减少和成本收益分别判断。测试通过不能证明模型必然遵守。
