Codex Team Runtime · Case Study

固件升级团队：可审查的协作闭环

一个跨前端、平台后端和下游后端的脱敏案例：先核实边界，再冻结契约；把提交、验收与实机结果分开记录。

阅读边界：本例展示协作方法，不把案例描述为 Runtime 功能的完备验证。代码交付与真实设备验收是不同阶段；HTTP 接纳也不等于设备升级成功。
01 · 协作结构

一个 Manager，三条项目所有权

用户 → Manager
范围与关键约束；唯一的派工、审查与验收所有者。
Manager → PDC / Base Graph
定位候选项目，再以需求、源码和当前基线核实。
固定契约 → 三个 Worker
前端、平台、下游按项目所有权并行。
代码验收 → 实机验收
前者不自动证明后者。
02 · 阶段审查

把问题留在可复现的证据链里

HTTP ACCEPTED 迟到

设备回包可能先到。较晚的接纳响应不能覆盖设备已知失败或新阶段；应答只更新它能证明的事实。

外部回执重试

接受、成功、失败回执独立持久化；重试不再下发设备升级。

鉴权过度设计

先核实已有网关、SDK 与租户边界。若现有边界已足够，删除专用实现而不是把复杂度固化。

验收分层

派工、发送、提交、接收、批准、合入、部署与实机结果分别记录。

03 · 统一团队工作台

两个页签，不能混用两类证据

页签展示内容不能推断
任务进度成员、任务、阶段、阻塞、提交与验收；来源为 state 与 Registry 投影。页面刷新不等于业务刚有进展。
指标统计经显式绑定的同团队日报中的每日 Token 与 MCP observation。无日报 / observation = 覆盖未知，不是 0

日报需要写明日期范围、时区、asOf、成员范围、来源与去重规则。直接 MCP 观察和原生日志观察可能重叠，不能相加；封装调用不可见时，也不能据此声称未发生调用。
